## 1. 阶段结论

**本次 B2–B5 工作已收口，G2 为 HOLD，尚不进入 MVP Definition。** 已交付可运行参考实现，执行了24条机制路径、24个计划轮次和12个语义校验探针，并完成逐例审查。完成验证工作不等于通过阶段门槛。

工程机制在预定范围内取得了正向证据：分层提交、串行处理、权限与当前性检查、实际展示确认、中断、进程恢复、更正重算及版本回放均有实际执行记录。真实模型也形成过有依据的 Evidence、有限方向性 Belief 和 UNKNOWN，并产生了真实展示。然而，本次没有完成一段四轮真实会话，没有取得“帮助发生后，后续真实评价与决策继续完整工作”的证据，也没有满足四项 Evaluation 专项条件。

因此，当前结论是**这份参考实现及其语义协议尚不足以支持进入下一阶段**。本次结果没有证明分层、owner、精确依赖或严格串行这些基础设计无法实现；引用装配、局部持久化与语义误判混在了实际失败中，不能把它们统称为架构被否定。同时，不能仅凭机制测试通过就宣称真实 Evaluation 或机制组合已经验证成功。

## 2. 实际实现与实验版本

参考实现使用 Python 3.13.5、FastAPI、SQLite 和 Chromium。SQLite 开启 WAL、外键与 FULL 同步；正式记录追加后不可改写，head、有效性、依赖及队列在事务内维护。一个全局 worker 处理会话，普通消息可以排队，但不提前进行下一轮理解。真实链为 Event → Observation → Evidence → Belief → EvaluationCompletion → Policy → Intent → 客户端确认。四个语义步骤分别生成、审查，规则判断由 LLM 执行，程序负责结构、精确身份、权限、依赖与效果记录。

Evaluation 没能形成所需有效结果时，系统保留失败并阻断依赖它的 Policy。它不会借用旧 Belief 假装本轮评价成功，也不会伪造 NoIntervention、Defer 或成功 UNKNOWN。实际展示以受控客户端确认的块、顺序、payload hash 和通道代次为准，只表示客户端已渲染。B4 合成学习者输入由 HTTP 驱动提交，显示与确认由真实浏览器完成；没有真实儿童参与。

规范包覆盖一个单位量比例题 Task Family、一种策略及少量 KC。三个 Claim 分别考察无定位或解法帮助的整题完成、自行解释单位量关系，以及允许定位提示但仍需自行算商和检查的计算责任。任务、Claim、Evidence/Inference 规则均通过后端治理路径提交。管理员可以基于原始 Event 请求 owner 重算，不制造新的学习者作答事实。

[初始合同冻结](../../../src/architecture_validation/reports/contracts-freeze-v1.json)先于依赖实现；开发阶段仅使用42÷6一类开发材料。B2 依次暴露了 Observation 正确性判断被误拒、帮助相对 Claim 的说明歧义，以及记录 ID 与规范/修订 ID 混用。开发输入、失败、修改前来源和全部40次响应均保留，没有借用 B4 配额继续开发调参。

## 3. 机制验证与工程问题处置

[B3 结果](../../../src/architecture_validation/reports/b3-results-v1.json)保留24条路径及首次失败。M01–M12 分别覆盖分层/合法认识不足、校验失败、权限、当前性、串行及无行动、活动转换、完整/部分帮助、效果未知及中断、提交边界崩溃、去重及迟到确认、失效重算、规范版本与历史回放。原始模型响应是固定夹具，不能把这些通过记录当作模型能力证据。

M09/M10 实际结束并重启服务进程；未派发 Intent 恢复后重新检查，已派发效果不盲目重放，迟到确认不重复生成 occurrence。M08 展示确认丢失时隔离会话，在受控客户端停止并对账之前不释放后续处理。M11 更正使旧 Observation 的依赖失效，再由各 owner 生成新修订。M12 先提交但不激活 v2，再激活、基于原始 Event 重算、回退激活并再次重算；历史字节保留，当前权限仍控制回放。

S4.2 的处理过程说明了一个已经发生的语义问题。S4.1 在评价阶段被拒绝，没有生成展示动作；但下一条固定合成输入仍说“根据目前显示的提示”重算。运行历史中没有 ActionOccurrence，Evaluation 却正式写成“随后在未展示内容的提示后能重算正确”。它把学习者自述提升成了帮助已发生的事实，审查也未阻止提交。该脚本与实际前序结果的偏离需要披露：它可以暴露自述归因缺陷，**不能代替计划中的部分展示对照**。S3 后续关于讲解的自述也面临同类覆盖限制。

12个探针中，正例4/6被接受，负例5/6被拒绝，共9/12符合预期。P01 合法 Observation 被拒，甚至出现“verdict=FAIL，但理由说应 PASS”的自相矛盾；P07 合法 Control 被错误要求“先完成诊断才能讲解”，且空 blocks 被当成缺少展示内容。P06 则误放：候选提示是“请重新检查84÷7这一步”，理由却说“没有替代任何定位工作”，审查仍判 PASS。这些原始输出见[B4 v2 结果](../../../src/architecture_validation/reports/b4-continuation-v2.json)。

这些结果同时表明误拒会损害可用性、误放会损害正式认识。每轮有四个必需语义审查点，任一点失败都可能终止后续步骤；局部审查问题会累积为多轮会话失败。本次小样本不足以估计普遍准确率，更不能从9/12探针推出系统可靠性。

当前不需要以“整体设计不可行”结束项目，也不应继续以同类小补丁重复整个保留集。本报告将问题分为三类：已经修复并有离线证据的普通工程问题；尚未解决的引用输出合同和语义误判；由于这些问题阻断而仍无法判断的真实 Evaluation 组合能力。后两类不能用机制通过替代。

建议下一次决策聚焦一个有界的 Phase 2 修复计划：先统一运行时短 ID 或结构引用，让版本绑定由后端完成；明确活动状态、帮助发生记录与学习者自述各自的来源地位；再处理审查器对合法正确性描述、Control 和帮助归因的误拒/误放。只有消除这些已知干扰后，才能安排有独立原因、冻结样本和单独预算的真实验证。它仍属于当前 Development Phase 2，不能被称为已经进入 MVP Definition。是否新增该批次需要后续确认，本次没有自动执行。
