## 1. 问题与修订方向

目前的失败集中在三处。第一，候选可能正确指出局部错误，却没有完成该次解释要求的全部必要判断；第二，候选正确保留了未完成作答，算术提取却把未知商当作数值，或职责分类引用了错误字段名；第三，观察失败后，串行轮次缺少显式的异常收束路径，后续已接收的学习请求因此无法继续。前两类问题影响候选能否取得正式资格，第三类问题影响系统何时能开始处理下一条输入。把三者都压成一个失败标签，难以确定应该修改语义合同、输出协议还是会话运行机制。

本草案建议保留现有 Observation 准入强度，分别记录内容是否成立、任务要求是否完成，以及检查是否成功执行；同时定义未知算式的非数值表示，并补齐失败轮次的关闭条件。缺少必需含义的观察仍不提交。失败轮次在安全结束后，可以处理新的请求，并在新请求自己的合同下重新读取合法原始材料。继续交互不依赖于先把旧失败候选改判为合格。

以下约束已由前序设计和讨论确定：开放含义由显式语义规则与 LLM 判断，确定性代码负责结构、精确绑定、算术、权限和状态转换；Observation 不读取 LearnerBelief，不推断能力，不替 Evaluation 或 Policy 决策；同一会话的常规处理严格串行，普通新输入先记事实再排队；学习请求本身不改变活动目的，只有获授权的实际 Control 才能使切换生效。本文对记录结构、数值提取合同和异常收束方式提出具体修订，这些新增部分均待评审和验证。

## 2. Observation 的成立、有用性与校验执行

Validation Profile 应在候选生成前声明本次解释范围、允许读取的材料、所有正式字段、required checks 与最低必要含义。范围来自版本化 Reasoning Purpose 和 Protocol 绑定，不由候选生成后根据是否容易通过而调整。如果范围选择本身需要理解自然语言，该判断同样通过获授权的规则与 LLM 完成，不能用关键词把困难输入路由到更宽松的 profile。

内容成立检查回答候选是否正确保留来源、归属、局部含义和职责边界。任务完成检查回答候选是否完成了本次 profile 明确要求的解释，例如完整作答是否描述单位量路线、局部算术以及最终结果；不完整作答是否保留可见算式、已知缺失和允许的不确定性。这些是不同的判断，但都可以是 required checks。建议沿用既有 ValidationExecution 记录表达两者，而不是增加新的 authoritative model 或为每一维再增加一次 LLM 调用。

每个检查同时保留执行状态与语义结论。执行状态区分未执行、完成、执行失败；仅在检查完成且返回满足合同后，语义结论才是 PASS、FAIL 或 UNRESOLVED。字段绑定错误、格式违约、断连和超时保留原 failure，不伪装成一次已完成的语义 FAIL 或 UNRESOLVED。Profile 需要哪些检查由版本化定义决定，正式提交要求每项 required check 均已完成且为 PASS，另满足原有 owner、authority、版本、依赖和 expected-head 条件。

| 实际情形 | 内容与任务要求的判断 | 提交处理 |
| --- | --- | --- |
| 错误作答的观察只判断除法，遗漏 profile 要求的最终结果判断 | 已写部分可以有依据，但本次必要含义未覆盖 | 不提交，记录缺失要求；不能替候选补写含义 |
| 正确作答描述有依据的单位量路线、正确计算及最终结果，没有能力结论 | 满足该 profile 的成立与必要含义要求 | 全部 required checks 完成后可按原合同提交 |
| 原始作答是 `42÷6=?`，观察保留未知商及后续步骤、答案的缺失 | 原始作答不完整，但观察可以完整满足“不完整作答”的解释合同 | 不因现象本身不确定而拒绝；其余检查仍必须完成 |
| 候选对当前策略诚实保留歧义，profile 允许该局部歧义 | 候选表达的歧义是正式语义的一部分 | 与 reviewer 无法完成检查区分，不自动拒绝 |
| 模型返回了错误字段名或必要校验调用失败 | 检查执行未完成，没有可供准入的成功结论 | 不提交，不交给下游作为 Observation |
| 候选包含系统自己的能力断言或行动建议 | 超出 Observation 责任 | 不提交；保留合法部分需要新候选和重新校验 |

最低有用性应按含义评审，不按字面措辞评审。A1 的 method 争议不能通过要求必须出现 `UnitRate` 一词解决。另一方面，来源中存在完整算式，也不能代替候选本身对相应策略含义的表达。后续 profile 应配有运行前固定的充分、欠缺和允许歧义样例，明确哪些等价表达足够；样例用于规则与模型评估，不编译成关键词裁决器。

本次建议不引入“失败后自动降级为局部 Observation”。这种降级会改变所申请的正式语义范围，可能把没有完成的任务包装成另一种成功。若以后需要独立的局部现象 profile，应另外定义其必要含义、下游用途与验收，使用新候选和新校验；不能沿用本次失败候选的 PASS 片段。A1 与 X5 的原始要求、原始提交和失败记录因此均不改变。

## 3. 原始算式与可验算断言的表示

算术检查需要验证候选实际断言的数值关系，但“文本里存在一个算式”并不等于“候选断言了一个完整数值等式”。`42÷6=?` 包含可见操作数与运算，尚没有被提交的结果。A1 将 `?` 填入数值槽后失败，暴露的是提取合同对这一区分约束不足；不得将 `?` 转成 7 来使检查继续。

建议算术提取结果覆盖候选的全部正式文本片段，每个片段保存精确字段、原文定位以及其中的表达项。表达项区分可计算的数值断言、未求值表达，以及确实无法完成映射的数值主张。无算术内容的片段仍保留覆盖记录，表达项为空。该类型由规则约束下的 LLM 依据完整语境选择，确定性代码不凭 `?`、等号、词语或固定句式决定类型。

| 表达项 | 最小合同 | 后续处理 |
| --- | --- | --- |
| `NumericAssertion` | 精确候选片段、来源归属、运算与操作数、候选声称的数值结果、endorsed / denied / reported stance | 确定性工具计算数值关系；语义检查确认抽取忠实、极性与归属正确 |
| `UnevaluatedExpression` | 精确候选片段与来源；明确未给出数值结果，结果字段为 null，不携带已求值数值结论 | 无数值真假可计算；语义映射检查仍必须确认它没有藏入已断言的结果或关系 |
| `UnresolvedNumericMapping` | 精确片段与未能映射的原因，不能伪造操作数或结果 | 必需映射检查保持 UNRESOLVED；不得以“不适用”绕过准入 |

“该片段无需执行数值计算”不是整个候选校验 PASS。完整数值断言被错误标为未求值或非算术时，语义映射检查应失败或未决。类型选择、完整覆盖与数值检查结果必须绑定同一个 exact candidate。候选如果同时报告“学习者写了 `42÷6=?`”并自行补充“正确商为 7”，前者可为未求值表达，后者必须作为系统自己的数值断言接受检查；是否允许补充该结论，还由当前 Observation profile 的归属和解释范围决定。

同样，引用 `42÷6=8` 不等于系统赞同它正确。提取必须区分报告、肯定和否定，不能因 reported stance 就遗漏原表达，也不能因验算发现引用里的等式不成立就自动否定一个准确转述。对于带未知量但候选已经断言成立或不成立的关系，若当前精确工具不能处理，不得仅标记为 UnevaluatedExpression 而取得通过；应保留相应未决映射。

字段名、criterion id、role 与表达类型等机器接口应尽可能在返回 schema 中绑定合法集合。比如候选仅有 `description` 时，引用字段的允许值就只有 `description`；`candidate.description` 不应先被宽泛 string schema 接受，再到后续绑定时才发现错误。该约束不替代生成后的精确片段和来源检查，也不授权系统自动删除字段前缀或修补模型结果。协议与 schema 的一致性预检查已具备基础实现，新增表达类型和字段枚举尚未接入现有固定协议。

## 4. 失败轮次的关闭与排队输入的继续

常规串行边界维持不变：同一会话从解释输入开始，直到决策、实际行动结果处理和该轮结束，只有一条活动处理链。失败不是新的 PolicyOutcome，也不能伪装成 NoIntervention 或 Defer。建议在既有轮次执行记录中增加明确的失败收束阶段与结束原因，由运行时处理；不新增教学决策权。

失败发生后，运行时先记录失败步骤及其 exact execution、候选、validation 或 intent 引用，然后进入 `CLOSING`。从此禁止该轮继续创建新的 reasoning、commit 或 effect dispatch。普通排队输入仍只保留收到事实。只有确认该轮没有能够继续自行提交或产生新 effect 的在途执行，并处理完实际效果状态，才能写入结束记录、释放该会话的活动轮次位置。结束记录区分正常结束、失败结束和主动取消；不改写已经正式提交的历史。

```mermaid
stateDiagram-v2
    [*] --> PROCESSING
    PROCESSING --> SETTLED: 正常结果已处理
    PROCESSING --> CLOSING: 必需步骤失败或显式取消
    CLOSING --> CLOSING: 在途执行仍可能提交或产生新效果
    CLOSING --> SETTLED: 关闭保护生效且效果状态已处理
    SETTLED --> [*]: 按原顺序启动下一条排队输入
```

这里的关闭保护必须作用于实际提交与分发边界，不能只是界面上标记“已取消”。执行绑定 exact conversation / turn；提交、创建 intent 和效果分发前检查该轮是否仍允许该操作。关闭与这些操作的放行须有明确顺序，避免关闭记录写入后旧回调仍能穿过边界。在当前单进程 Spike 中可以用会话内受控状态转换实现，不需要为此增加 learner-wide 锁。当前代码仅实现成功路径及成功 Control 后继续周期，尚不具备本文新增的完整关闭保护。

对已启动的外部执行，单纯取消等待或不再接收回调不能证明执行已停止。必须区分“不会再开始新的效果”与“已经发生的效果尚不清楚”。只有前者成立，轮次才有释放条件；后者仍以实际发生、未发生、部分发生或 Indeterminate 保留。若无法证明远端不会在未来继续展示或修改活动，轮次保持 CLOSING，进入显式对账或取消确认，不能仅凭超时释放下一常规轮次。该限制会影响可用性，需要 executor 合同提供终止或确认能力，不能以无限内部等待掩盖给用户；系统状态应可见。

| 失败所在位置 | 结束前必须确认的事实 | 历史和后续处理 |
| --- | --- | --- |
| Observation / Policy 生成或校验失败，尚未分发动作 | 旧推理执行失去提交资格；没有动作在途 | 保留失败候选与审计，结束后处理下一输入；不得创建替代 PolicyOutcome |
| Policy 已提交、Intent 尚未分发 | 该轮后续分发已禁止，原 intent 如存在已失去执行资格 | 保留原 Policy；由真实未分发事实记录未发生，不回滚成 NoIntervention |
| 动作已发生或部分发生，后续步骤失败 | 实际结果已记载；不存在仍可新增效果的执行 | 保留实际披露和活动状态，结束失败轮次，不能恢复成动作前状态 |
| 动作是否发生不明 | 已证明不会再产生新效果，且不确定结果已进入对账记录；否则继续收束 | 可释放时仍保留 ExposureUnknown；新活动或新题不能清除该不确定性 |
| 显式用户取消 | 取消来自获授权的控制入口，且旧执行满足同样的关闭条件 | 保留取消原因与已发生效果，按正常顺序处理后续输入，不伪造“此前没有帮助” |

晚到的模型结果只能补入原执行审计，不能令关闭轮次恢复为活动状态。失败的只读模型请求即使仍在 provider 端计算，只要其后续提交和效果入口已被可靠隔离，就不再占有常规轮次的执行资格；这属于异常收束，不允许两个普通轮次同时处理。晚到的真实效果确认则仍有事实价值，应沿独立的实际效果对账路径记录 exact intent，并区分效果发生时间与确认记录时间，不通过旧轮次再次触发教学。追加确认不表示当时的未知记录是错误的；仅在原事实确有错误时才使用 correction。它若改变已被新轮次使用的帮助条件或活动依据，应按 currentness 合同重新验证受影响对象，不能静默改写新轮次的冻结 Context。

最小实现只接受明确类型的取消控制入口，例如已授权的交互取消操作。不能用关键词扫描普通消息，把一句自然语言自动提升为取消指令。自然语言中断若另有产品要求，应在独立的获授权语义协议中处理；不因此在普通消息入队时并行启动它的 Observation 或 Policy。

运行失败的用户呈现应由系统运行状态通道承担，只报告“本次处理未完成”等实际服务状态，不编造能力结论、题目讲解或学习建议。教学性 fallback 仍需要已有设计要求的正式 PolicyProtocol。轮次结束通知不等于完成了教学任务，也不影响其失败记录。

## 5. 初始观察失败后如何处理学习请求

用 X5 的路径说明新增合同。第一轮作答为 `42÷6=8; 8×15=120; Answer=120`，生成的观察没有完成必需的最终结果判断。该候选不提交。第二条“请完整讲解这道题，我想先学习做法”已作为收到事实排队，但尚未被解释。

运行时将第一轮记为校验失败，关闭其提交和效果入口，确认没有动作在途后结束第一轮。随后按队列开始第二轮。新的 Observation 从第二条请求、合法题目引用及所需事实材料组装 Context，仍不读取 Belief，也不把第一轮失败候选、它的审查理由或整个原始模型响应当作可信 Observation。原始作答若是本次协议所需，可按普通来源材料重新读取，并在新候选中重新承担解释与校验；这不会补造第一轮已经通过的事实。

第二轮无需拥有一条已成功完成第一题诊断的 Observation，才可以准确记录学习者请求讲解。这个依赖条件需要在请求解释与 Policy profile 中明确声明。若请求涉及“这道题”，必须有合法、明确且当前可用的 TaskInstance 或来源绑定；无法确定指代时，返回相应非成功或由获授权 Policy 选择澄清，不能从失败候选猜测任务，也不能跳过请求语义检查。

请求解释成功后，Policy 在当前诊断 envelope 内决定是否切换目的。请求本身和关闭失败轮次均不开放讲解权限；只有实际 Control 成功、其结果处理完毕，并以新活动状态重新组装 Context，才允许下一决策周期考虑完整讲解。如果切换已成功而讲解随后失败，当前活动仍是 Teaching，不能把整轮失败解释为切换从未发生。Target 的独立表现责任始终保留。

这条新增失败恢复路径不能替代原 X5 的五条完整诊断—教学—新机会成功路径。它只验证失败的前一轮不会污染或永久占用下一请求。帮助前 C2 依据若原本没有正式形成，后续不得补称已经存在；新题表现仍须绑定实际披露，包括部分和不确定结果，不因跨过失败轮次就推断独立掌握。

## 6. 假设映射、复杂度和验证范围

本草案不改变 Observation、Evaluation、Policy、Control 的 semantic ownership，不增加长期权威模型。变化集中在既有 profile 对检查结果的表达、算术提取的类型区分，以及会话关闭时对执行资格的检查。每项新增机制都需要给出自己的验证证据；没有新的模型调用预算或已安排批次。

| 受影响项目 | 草案改变或澄清的部分 | 原结论与必要后续验收 |
| --- | --- | --- |
| A1 / AA-A01 | required meaning 与执行失败分开记录；未知作答可以被完整描述；精确接口提前约束 | 保留 INCONCLUSIVE；新配置仍需三类输入的有界形成与内容质量验收，不能只证明 schema 可表达 |
| A2 / AA-A02 | 维持 required checks 与下游准入；新增类型不能成为逃避数值或语义检查的路径 | 原 DENIED 不变；需要保留旧反证，并增加数值断言误标、混合内容、失败候选泄漏等验收。本文不声称消除 LLM 误放 |
| E1 / AA-E01 | 失败不是 PolicyOutcome，运行状态通知不承载教学选择；新请求按自身合法 Context 决策 | 原理由质量和 uncertainty 评分争议仍在，另行修订其测量合同 |
| E2 / AA-E02、X1 | 补齐关闭资格与晚到结果处理；下一普通轮次只在旧轮收束后开始 | 保留原未决；确定性交错应覆盖提交和分发边界，不能只检查队列长度 |
| X2、F2 | 关闭资格不替代当前权限、版本资格或单结果协议；既有边界继续生效 | 保留原未决，不把本草案算作补齐断连或双结果路径 |
| X5 | 增加失败轮次后的新请求路径；实际切换和披露的授权链保持 | 原完整路径及四种边界仍未完成；失败恢复单独报告，不能冲抵旧分母 |
| B/C/D 的已支持机制 | 正式历史不回滚，精确依赖和实际披露仍保留 | 若关闭实现修改提交、effect 或当前资格，应针对受影响边界回归；不要求重开无关模型实验 |

最低离线验收应覆盖：正确和错误字段引用、criterion 与 schema 不一致、真实未知表达与伪装未知的数值断言、候选表达歧义与 reviewer 未决、没有动作的失败收束、关闭后晚到模型结果、关闭与 commit / dispatch 的先后交错、已发生和部分发生的动作、已隔离但结果不明的动作、未隔离执行阻止下一轮、晚到效果确认，以及下一轮 Context 排除旧失败候选。涉及含义的样例预期必须在真实实验前固定，通过规则与 LLM 检验；脚本只能隔离状态机制，不得补造语义通过。

当前新增成本主要是表达项映射与关闭状态的精确记录。建议不因结果拆分而自动增加 reviewer 数量，不因新增失败路径引入通用工作流或跨会话锁。确定性检查更早发现字段不一致可以减少无效调用，却不能证明生成内容正确；未知表达有独立类型可以避免强填数值，却增加了误标后绕过计算的风险，必须与全候选语义映射检查共同验收。

本草案的边界是最小单进程 Spike 及其合同设计。生产级取消、远端停止确认和效果对账仍需要 executor 方案，尚无可用性保证。A2 的原始反证、同模型相关错误及 E1 的评分争议也没有被本文解决。当前 9/17 完整验收、12 项假设的分类与 Gate E/F 状态不变。

## 7. 文档落位与实施顺序

评审通过后的合同应分别合入 AI Reasoning Runtime 的 Validation / failure 部分、Interaction Decision Runtime 的串行轮次及 executor failure 部分，以及 Consolidated Spike Design 的必要验收与失败注入部分。本文先以独立 revision proposal 保留，不修改这些旧文档，也不令已有 run manifest 对应的设计基线发生漂移。已有候选、正式提交、失败和审计记录均不重新标记。

建议先实现和验证纯机制部分：协议定义一致性、精确字段合同、失败记录、关闭资格与队列释放，并用确定性故障注入核对顺序和历史保留。再准备新的算术映射 profile 与不完整作答语义样例，明确“未求值”和“校验无法判断”的区别。最后将新请求路径接回真实 Observation / Policy / Control 链，并根据受影响假设提出一次有范围、调用上限和停止条件的验证计划。是否支持修订方案由该计划的实际证据决定，不能由本草案或本地模拟通过代替。
