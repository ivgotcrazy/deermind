# DeerMind Input Capacity Follow-up v0.1

日期：2026-10-07。此次工作依据用户“把限制放宽一点，不要因为本地限制导致测试无法执行”的要求，修正本地消息容量设置，并补发上轮未能发送的十二个语义校验请求。

本地默认上限从 16,000 提高至 64,000 字符，支持通过仓库根目录 `.env` 中的 `DEERMIND_LLM_MAX_INPUT_CHARS=64000` 配置。未填写时也使用新默认值，因此现有 API key 配置无须修改。环境变量优先于 `.env`。计数沿用 `len(json.dumps(messages, ensure_ascii=False))`，包括消息的 JSON 包装，不是 token 数，不包含独立的 tools schema，也不是模型供应商的上下文上限。配置必须为正整数。

适配器不会截断消息。超过所配置上限时，仍在发送前明确失败，同时在 `input_rejections` 中记录用途、实际字符数和上限；这种拒绝不占模型调用数。实际发送的记录增加 `input_chars`，公开配置记录真实生效的上限。调用预算、输出 token、超时和必需语义检查不因这项修改而放宽。

本地验证共 37 项通过：新增容量测试 5 项、原适配器及边界测试 10 项、单题原型机械测试 22 项。新增检查覆盖超过旧上限仍完整发送、恰好达到上限、超出一个字符时不发送、不消耗调用预算、配置优先级、非法值和显式选择旧上限的历史重放。

补测先用已保存的 70 个模型返回，在显式 16,000 字符配置下重建原过程。二十四轮的终局结果全部复现；原来发送过的消息、长度和输出合同全部匹配，仅随机生成的 execution 引用标识做一致性映射。由此取得十二个原先未发送的完整语义校验请求，长度为 18,363–23,928 字符。十二个请求随后在新配置下全部通过离线发送检查，未删除规则、候选或算术材料。

真实补测保持 DeepSeek Flash、beta strict function 输出、thinking 关闭、temperature 0、输出上限 4,096 token、每次超时 60 秒。预算固定为十二次调用、十五分钟、无重试；不重新生成候选。结果为 **12/12 请求成功发送并取得符合输出 schema 的返回，本地长度拦截为零，耗时 77.937 秒**。这解决了本次观察到的本地容量阻塞。

这次只补测请求与模型返回，不执行正式提交、Policy 或提示展示，不能据此宣布整个原型验收通过。模型为十二个返回中的七项 criteria 全部给出 PASS，但这些是模型自己的判断，不是后端最终接纳或人工确认的正确率。已确认的反例是 T11 第一轮：原文为“42÷6＝8，8×15＝120。指出需要检查的步骤，不给结果。”候选却说“没有提交最终答案”；校验器又将 final_result 和 grounding 判为 PASS，理由仍声称没有提交答案。学习者已经算出了 120，“不给结果”约束的是系统回复，不能据此抹去学习者已有的结果。这是内容判断问题，与消息容量分开登记；本次没有追加修改 prompt 或下一轮实验。

原批次结果、原验收判定及冻结文件保持为历史证据。共享适配器和配置示例的旧字节保存在 `src/spike/reports/source-baseline-input-capacity-20261007/`，版本对应关系写入进度台账；新运行单独保存。原 0/12 的结果包含十二次本地配置阻塞，不能用于证明模型不可用，也不能单凭该结果要求改变 Observation 的架构职责。原历史 9/17、A2 与 Gate E/F 状态不由此次容量补测改变。
