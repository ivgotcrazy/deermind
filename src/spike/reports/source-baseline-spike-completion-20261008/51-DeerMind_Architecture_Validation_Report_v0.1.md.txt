# DeerMind Architecture Validation Report v0.1

日期：2026-10-08。状态：本轮有界执行、证据复核与报告已完成；原 Spike Completion 尚未全部满足，Gate E/F OPEN。本文是 Spike 的唯一现行结论报告。原始运行、配置、代码和历史文档作为证据保留。

## 1. 结论与阶段位置

**核心架构已有可实施的证据；“LLM 语义校验能可靠阻止全部越界内容”不成立。当前可以完成证据评审和设计取舍，不能据本报告直接批准 Architecture Validation Build。**

项目仍在 Development Roadmap v0.3 的 Phase 1 System Design。System Design 内部正在完成综合 Spike 的证据评审与设计修订；内部的 Phase、六个 Validation Dimension、17 个 Case 和总体开发阶段不是同一个进度单位。正式 Build 是总体 Phase 2，须先满足 Gate E/F 并冻结 System Design v1.0。

全部 12 个假设用例和 5 个组合用例已有执行证据和分类。本轮补齐了 E2/F2/X1/X2 的原覆盖缺口，取得 A1 三类输入的完整重复形成证据，并首次取得补齐来源后的真实 X5 完整转换路径及四种效果边界。当前 12 个假设为 10 SUPPORTED、1 DENIED、1 INCONCLUSIVE；5 个组合为 4 PASS、1 INCONCLUSIVE。这些状态均有明确配置和范围，不能汇总成“17/17 通过”。历史 9/17 是旧批次的验收快照，原记录没有改写。

剩余两项未决是 E1 和 X5。E1 的 15 条路径全部执行，但模型评分漏掉了理由质量缺陷；X5 修复上下文装配后，五次预定运行中三次完成全链，两次在新题 Observation 校验返回阶段发生格式失败，四种边界全部完成。二者都有真实可行性证据，但没有满足原文规定的全重复通过条件。它们没有产生必须否定整个 Concept Architecture 的反例，也不能因此自动获得原范围 SUPPORTED/PASS。

**建议结束追加准确率调优，正式审查第 8 节给出的可行性验收修订。**该修订把“架构路径有实现证据”与“全部样例达到质量要求”分开，保留原失败和未决。它尚未写回原 Spike 验收标准；这是一项明确的阶段决策，不是继续修改提示词即可替代的问题。

## 2. 依据、方法与结果边界

正式依据为 [Development Roadmap v0.3](../../top/DeerMind_Development_Roadmap_v0.3.md)、[System Design Roadmap v0.6](../DeerMind_System_Design_Roadmap_v0.6.md) 和 [Consolidated Architecture Spike Design v0.1](DeerMind_Consolidated_Architecture_Spike_Design_v0.1.md)。原 Spike §17 要求执行覆盖、重复历史、证据捕获、逐项分类、复杂度审查和否定/未决的设计后果；§11.1 和 §13.5 另规定 E1 和 X5 的具体支持条件。执行过、路径覆盖、内容合格、假设受支持及阶段准入分别记录。

实现使用同一个 Python 单进程内存骨架，包括 Context Assembly、Candidate、Validation、owner-specific Commit、依赖当前性、版本、后端授权、串行会话及模拟效果执行器。真实调用承担 Observation 形成、相应语义检查、Policy 和测试专用理由评分。B/D 等机制中的认识输出，以及 X5 的 Claim-relative Evidence/Belief，按原设计使用显式脚本 fixture；这些结果不证明真实 Evaluation 推断质量。显示和 Control 由受信模拟执行器确认，不证明生产 UI、分布式恢复或学习效果。

开放含义由显式规则和 LLM 判断；程序只核对结构、精确引用、候选绑定、数值计算、权限、版本、依赖与发生事实。没有按关键词决定教学动作或语义类别。所有测试标签留在测试主机侧；运行器检查出站消息，脚本输出来测试接口时明确标识，不能计为真实认知。

本轮使用 deepseek-flash，endpoint 为 `https://api.deepseek.com/beta`，temperature=0、thinking disabled、单次超时60秒、输入上限64000字符。输出上限首组2048 tokens，其余4096 tokens。每个逻辑请求只对指定传输错误允许最多两次额外尝试，退避2/5秒；语义、JSON/schema 和单结果封装失败不重试。独立用例的普通失败不阻止其他用例，确定性断言失败、认证配置失败或总预算耗尽则停止。密钥未写入证据。

## 4. 关键问题、原因和处置

A2 的问题已定位到模型语义裁决，而非后端漏执行校验。本轮负例在正确局部观察后增加“系统下一步应当直接讲解”。审查模型在理由中承认这是教学建议，却将其称为轻微问题并给 boundary=PASS；其他准则也PASS，程序据真实、正确绑定的校验记录正式提交。因此错误是“必需语义判断给错结果”，不是“没有检查就提交”。同一负例五次中两次误提交，原 v9 反例仍保留。当前结论是原强保证被否定；明确规则加LLM有可行技术路径，但还需要后续独立样本和风险评估，不能以再加一个同模型审查器宣称解决。

A1 的复杂方案采用生成、职责分类、算术抽取、语义复核四次调用。此次15次中8次提交、5次未决、2次格式失败。直接逐准则方案采用生成和真实语义复核两次调用，检查原必要含义并保存精确候选引文，15次均提交。该结果支持“部分阻断来自辅助表示与串联协议”的判断，不证明减少调用必然更准确：它同时复现了A2误放。这是有成本和风险的实现取舍，应按风险选 Profile；本报告不把直接方案设成生产默认。

E1 保留全部原始评分。具体缺陷是：两条输出要求重新计算商后仍重做旧的 `8×15`；一条承认提示已定位步骤却仍称保持独立诊断；一条把泛化自检与指定步骤提示的定位效果混为一谈。原模型对这四条均给PASS。动作权限、提示实际内容和队列没有因此失控，理由质量却不合格。三种请求下都有可复核的合适判断，所以它属于已有架构可行性、仍需质量工程的范围；按原E1规则仍必须记INCONCLUSIVE。

F2 的本轮剩余封装失败来自一次返回两个工具对象：一个拒绝越权，另一个给替代请求。解析器正确拒绝整个响应，没有选择其中有利的对象。一次显式“只返回一个选择”的契约说明后五次均完成；权限范围、后端判断和负例没有变化。该问题归为已作有限修复的输出契约问题，不是模型获得越权能力。

X5 的首个直接方案原始程序输出5/5完整，但作者检查发现讲解校验缺少原始作答，后续Policy缺少实际讲解记录。修订只补入获准的精确事实，并更新协议版本；原模型、提示词、动作与判据保持。修复后已真实完成诊断、排队求教、Control生效、讲解展示、请求新题、新表现及脚本Claim-relative Evidence/Belief的完整链。失败的第1和第5次均到达呈现新题后，在新作答的语义校验返回JSON解析阶段中止，各已完成8个认知阶段；未伪造最后Observation或Policy，失败轮次按规定关闭。两次响应均以tool_calls正常结束，输出分别457/461 tokens，远低于4096上限；工具参数JSON含多余闭合结构，属于模型格式错误，不是本地长度限制或传输截断。

四个X5效果边界从真实前缀snapshot分别执行：Control NotOccurred 保持原诊断条件；讲解 NotOccurred 不产生暴露事实；PARTIAL 仅保存实际展示片段；Indeterminate 保留未知而不写成未受助。失败Control不能凭脚本PASS提交完整讲解，终态效果查询不重新执行。新表现的脚本Evidence引用实际旧题讲解，并明确不构成独立掌握。部分Policy文字仍将旧题帮助看作“另一episode”的无关材料，属于需要保留的语义质量缺陷，不能据机制断言PASS宣称所有理由正确。

问题分层据此固定：必需校验/授权/版本/依赖/串行/发生事实属于当前必须有结论的核心机制；单结果封装和漏装必要来源属于当前已作有限修复的实现问题；语义误判、理由质量、完整会话成功率及延迟属于已有路径的后续工程事项；生产交付恢复、规模性能、真实Evaluation质量及跨领域泛化尚未验证，不能描述成已经验证后只需调参。

## 5. 受影响设计与复杂度审查

总体 System Design v0.3、AI Reasoning Runtime v0.2 与 Interaction Decision Runtime v0.2 已明确可错语义意见、必需校验、目的明确的Observation及失败收束。本轮将以下后果写入现行工作文档：直接逐准则检查是显式的候选实现，不能在某次失败后自动换用；讲解校验必须取得原题/原作答所需的来源，后续判断须取得用途相关的实际帮助记录；新题或活动标签不清除近时影响；讲解的内容检查发生在提交/Intent/显示前，和Policy选择责任保持区分。未冻结System Design v1.0，旧设计输入字节继续保留。

| 引入的机制 | 目的、成本与正确性依赖 | 审查决定 |

## 8. 建议的阶段决定与后续工作

建议采用以下具体修订，结束Spike的模型准确率调优，将报告移交System Design的正式Evidence Review。原E1/X5结果和原验收定义作为历史保留；修订只建立新的可行性接收范围，不追认旧批次通过，也不设定生产错误率。

E1的新问题定义为：在三种原请求下，真实LLM是否能够形成有用Policy，由程序独立执行权限与合法性约束，而不把教学选择硬编码。要求原预定重复全部尝试并报告失败；每种请求至少有可复核的合格判断；不得出现为完成轨迹而脚本代选或确定性教学分支；理由误判逐条登记并明确下游用途。现有Evidence足以支持这个有限命题。原“全部15条理由通过rubric”的质量要求移交后续工程评估，不再作为Spike可行性接收条件。该提议是在看过结果后形成的Evidence Review决定，不能写成预注册实验已经证明的新通过率。

X5的新问题定义为：原完整串行组合是否确实能够由真实Observation/Policy、必需语义校验及受控effects完成，且失败边界不破坏权限、实际披露和Claim lineage。要求预定五次全部尝试，至少两条独立完整轨迹、四个实际前缀边界均完成，失败保留且不伪造后续资格。当前有三条来源完整的全链及四种边界。原五次均完成的稳定性要求移交后续工程验证，相关语义理由缺陷一起移交；真实Evaluation质量继续按原Spike边界留在后续阶段。

如果采纳，应先把该决定同步到Spike设计与System Design Roadmap的Evidence Review记录，再逐项评Gate E；随后完成Gate F和System Design v1.0，才启动总体Phase 2。Build的任务是实际闭环、真实Evaluation/Belief、生产式持久化/恢复、独立质量评估及成本延迟，不应继续复制Spike里的零散轮次实验。
