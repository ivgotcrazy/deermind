## 1. 本阶段要回答的问题

Build 要回答的是：在一个真实运行的小系统中，事件记录、模型理解、语义校验、交互决策、实际展示、学习者评价和历史恢复能否组合工作，以及这种组合需要付出多少时间和工程成本。完成标准是一套可运行参考实现及一份说明能力、失败和适用边界的验证报告。报告支持项目 G2 判断；G2 通过后才进入 MVP Definition。

Spike 已完成，系统设计 v1.0 已经冻结。Spike 中 A2 的绝对语义隔离假设被否定，E1 的广泛教学判断质量和 X5 的完整会话可靠性仍未决；这些结论不因进入 Build 而改变。Build 承接的是修订后的合同：语义判断采用显式规则约束下的 LLM，判断可能出错；权限、提交资格、版本绑定、实际发生记录和责任归属由确定性机制执行。发现语义误放需要记录并更正，不能把它解释为获得了行动权限或学习者能力事实。

本方案采用单进程 Python 后端、本地 SQLite、简单浏览器界面和真实模型适配器。实现规模限定为一个合成学习者、一个数学 Task Family 和有限交互。验证分为可重复的机制检查与一次有预算的真实模型测量：机制检查必须满足合同，模型测量按固定样本给出成功率、缺陷和不确定性。两类结果分别报告，不用模型评分替代事务与权限检查，也不要求模型达到百分之百正确才结束本阶段。

本文完成 Build 工作项 B1。后续顺序为 B2 最小真实闭环、B3 组合与恢复验证、B4 质量与成本测量、B5 报告与 G2 评审。这里的 B1–B5 是 Build 工作项，与 Spike 中同名假设编号无关。

## 2. 最小场景与能力边界

### 2.1 验证场景

领域材料采用“先求单位量，再按数量缩放”的正比例应用题。一个 Task Family 包含数值和叙述不同的实例；主要策略固定为单位量法，KC 只覆盖本任务需要的单位量关系、除法计算与比例缩放。任务、策略、KC 及其关系由一个受治理的初始规范包提供，模型不能在普通交互中自行修改。它们用于测试架构，不代表已经确定产品首发学科、年级或课程内容。

最小例子是“6 本练习本共 42 元，15 本多少钱”。学习者提交“42÷6＝8，8×15＝120”，随后请求“指出需要检查的步骤，不要给答案”。系统需要保存原始作答，形成有来源的 Observation，再由 Policy 判断是否提供提示。若展示“再检查一下 42÷6”，发生记录必须包含实际展示的文字；评价时可以认为定位受到帮助，同时保留学习者重新计算的责任，不能声称完全没有帮助定位。

后续输入可以是改正后的计算、请求讲解，或者同一 Task Family 的新题。请求讲解可能结束独立诊断并进入教学，但请求本身不等于讲解已经显示；只有实际活动转换完成，新的教学决策才能沿新上下文执行。新题也不会自动清除近期帮助的影响。Build 必须把这些区别落实到记录和运行结果中。

### 2.2 本次交付的范围

| 范围 | 本次实现 | 边界 |
| --- | --- | --- |
| 学习者与输入 | 一个合成学习者，文本作答、提示或讲解请求、更正、主动中断 | 不使用真实儿童数据；不做语音、图片识别及账户体系 |
| 交互 | Solve 场景中的独立诊断与教学状态；有限 Hint、Explanation 和必要的活动转换 Control | 保留 Execute、NoIntervention、Defer；不做开放工具代理与多步教学规划 |
| 评价 | 面向本任务的 Task Proficiency Claim，以及少量 KC Claim；真实 Evidence 解释和 Belief 推断 | 缺乏证据时允许 UNKNOWN、NonInformative 或保持原 Belief；不输出未经校准的掌握概率 |
| 状态与历史 | 持久化事件、正式修订、依赖、执行记录、展示结果；更正、失效和重建 | 本地进程重启恢复；不证明磁盘损坏、跨机容灾或分布式吞吐 |
| 版本与权限 | 一个规范包初始化、一项受治理的版本切换及回退；后端授权、撤销和历史访问检查 | 测试身份来自明确的本地可信启动配置；不冒充产品级身份和治理平台 |

Evaluation 的初始 Claim 包至少区分“无定位或解法帮助时完成本类任务”与“在规定支持条件下执行相应计算”。最终定义需明确对象、条件、责任边界、质量要求和可接受反证，并在首次真实运行前随规范包冻结。不能为某次提示临时创造新能力标签，也不能把一个正确答案直接记为掌握了三个 KC。准确率、延迟和会话完成率属于本阶段测量对象；学习收益、长期保持和真实用户价值留给后续产品与试点阶段。

## 3. 组件与存储设计

### 3.1 实现结构与技术选择

采用一个 Python 应用进程，通过 FastAPI 提供受限 HTTP 接口和静态页面；浏览器以 HTTP 轮询获取轮次状态及获准展示任务。FastAPI 在这里承担接口定义和结构校验，教学判断仍由业务 Protocol 负责。[FastAPI 官方功能说明](https://fastapi.tiangolo.com/features/)支持其基于类型声明的接口与校验能力，不能据此推断其能校验教学语义。

SQLite 数据库保存在本机磁盘，采用短事务和串行写入。这个选择减少独立数据库服务及消息基础设施的部署成本，适合单进程、低写并发的验证范围；SQLite 的单写者约束也要求模型请求与浏览器等待全部位于数据库事务之外。[SQLite 适用场景](https://sqlite.org/whentouse.html)和[事务隔离说明](https://sqlite.org/isolation.html)是该实现选择的依据。多实例写入或更高可用性需要重新评估数据库与调度方案，本轮结果不外推到这些场景。

运行环境、Python 和依赖版本在 B2 建立可运行工程时锁定到依赖文件，并进入运行清单。使用 `sqlite3` 显式管理事务，启用外键检查、WAL 和持久化同步设置；启动时核验实际设置。受限浏览器只展示已经获准的纯文本块，不直接执行模型生成的 HTML、脚本或函数。模型调用使用独立适配器，复用已有环境变量约定；普通输入接收与中断接口不能被同步网络请求阻塞。

以下是逻辑组件划分。它们可以在同一进程、同一数据库中实现，存储共享不会改变语义 owner。

| 组件 | 输入和输出 | 写入责任 |
| --- | --- | --- |
| 事实接收与会话调度 | 原始输入、客户端确认、管理事件 → 事实记录、持久队列、轮次状态 | 接收事实及运行状态；不产生 Observation 或 Belief |
| 规范与权限管理 | 初始规范包、授权决定、版本激活和撤销 → 可解析的版本与权限 | 按所属 Space 写规范版本，按治理授权写激活记录 |
| 上下文与当前性解析 | Purpose、精确引用、授权范围 → Context Package、Version Context、DependencySet | 保存执行快照；不将快照变成新的学习事实源 |
| AI Runtime | 固定 Protocol、上下文、模型配置 → Candidate、ValidationResult、ExecutionRecord | 保存尝试及校验记录；正式提交交给对应 owner |
| Interaction | 事实和规范语义 → Observation、PolicyOutcome、ActionIntent | 单写交互认识、决策和行动意图；不写学习者 Belief |
| 展示与效果执行 | 获准 Intent → 实际展示确认、NotOccurred 或 Indeterminate | 记录事实上的发生结果；不重新选择教学动作 |
| Evaluation | Observation、Claim、实际帮助和已有 Evidence → Evidence、Belief 或无修订结果 | 单写 Evidence 与 Learner Belief |
| 依赖、重算和审计 | 修订、撤销、版本变化 → 当前性保护、重算任务、历史视图 | 管理有效性和执行资格；不自行发明派生内容 |

所有公开写入口调用明确 owner 的命令服务；通用数据库写接口不暴露给模型或浏览器。可信测试驱动可以制造外部撤销和故障，但只通过显式管理接口及测试模式执行，不能用消息正文中的“管理员”字样获得权限。规则、校验代码、Protocol 及规范包分别有版本，避免把全部变化压成一个系统语义版本。

### 3.2 持久化与事务边界

数据库至少保存六组记录：事实与原始材料；规范版本、治理决定和激活记录；Context、模型执行、候选及校验；Observation、Evidence、Belief、Decision 等正式修订；精确依赖、当前 head 和重算任务；会话队列、检查点、Intent、派发及效果确认。原文和小型材料与其 hash 一并存储；日志用于诊断，不能成为恢复正式状态的唯一来源。具体表列在 B2 的 schema 与迁移文件中维护，不另外创建一份同内容的过程文档。

每个正式修订至少携带对象及修订标识、owner、内容 hash、来源引用、Protocol 与语义版本、Context 和 Execution 引用、DependencySet、校验引用和提交记录。每个依赖都声明其用途及 CURRENT 或 PINNED 语义。引用不能只保存“当前 Observation”这样的可变名字，也不能在提交失败后把旧 Candidate 换绑到新输入。

提交事务重新读取 expected head、关键依赖、生命周期、权限和必需校验，成功时原子写入新修订、当前 head、依赖和后续运行任务。Observation 更正、权限撤销或版本影响导致失效时，事务必须先阻止相关旧对象被作为 current-valid 输入或 effect 依据，再排入重算任务。当前小规模实现可在事务内遍历依赖闭包；重算内容在事务外生成，然后按正常提交合同写入。模型等待期间不持有写事务或整个学习者的数据库锁。

事实 occurrence、输入幂等键、对象 revision、Intent 派发身份及效果确认均有唯一约束。数据库中保存检查点和待办，可在进程重启后识别尚未提交、已经提交但尚未派发、已经派发但结果未知等情况。数据库提交成功但客户端没有收到成功响应时，再次提交相同幂等键返回已存在记录，不创造第二次发生。

### 3.3 最小接口与旧代码边界

| 接口类别 | 必需参数与行为 |
| --- | --- |
| 提交输入 | session、客户端消息标识、正文和材料引用；返回接收及排队状态，不同步返回教学结论 |
| 查询轮次和展示任务 | session、游标、已建立的通道身份；只返回当前获准状态与精确 payload |
| 确认展示或停止 | intent、dispatch、通道代次、payload hash、实际块标识及确认类型；拒绝错绑与重复副作用 |
| 中断当前轮次 | session、目标 turn；撤销旧轮新增提交和派发资格，并进入效果收束 |
| 更正、撤权、激活 | 后端验证的管理身份、精确对象及 expected head；模型内容不能调用或授权这些接口 |
| 历史与验证导出 | purpose、授权范围和精确执行标识；区分原始记录、重建与新执行 |

新工程拟放在 `src/architecture_validation/`。已有 `src/spike/` 保持实验和历史证据用途；可移植经过审查的模型传输、严格 JSON 解析、来源引用及数值运算代码，但 Build 运行不依赖导入 Spike 历史快照。内存状态、脚本 Evaluation、固定 Policy 答案和模拟显示只允许用于明确标注的机制测试。它们不能参与真实模型组，也不能计为真实闭环完成。

## 4. 正常运行与异常处理

### 4.1 一轮处理如何完成

同一会话的普通输入严格排队：接收事实可以立即落库，但只有当前轮收束后才对下一条输入组装语义上下文、调用模型和作出决策。后台重算与外部管理变化仍可能发生，因此严格串行不能替代提交和执行前的当前性重验。单个服务实例通过进程独占及数据库中的恢复代次防止重复调度；Build 不启动第二个活动 worker 实例。

本实现选择在一个普通作答轮次内，先完成 Observation，再更新该作答涉及的 Evidence 和 Belief，最后进行 Policy 判断。这样本轮 Policy 能引用刚完成且兼容的评价结果；如果评价无法形成 current-valid 结果，则按所需输入合同选择 non-resolution，不能偷偷读取旧 head。某条请求没有新的表现证据时，Evaluation 可以形成 NonInformative 或不修订 Belief 的显式结果。所选调度顺序是本 Build 的实现决策，不改变总体设计允许的其他调度方式。

| 步骤 | 输入 | 处理与输出 |
| --- | --- | --- |
| 1. 接收 | 题目引用、学习者原文、消息幂等键 | 写入收到的事实、原文和队列；到达队首时创建 turn 与执行代次 |
| 2. 理解 | 本轮事实、获准题目及策略语义、Observation Profile | 生成 ObservationCandidate，完成结构及语义校验，由 Interaction 提交；不输入旧 Belief 或旧 Policy 理由来解释原始作答 |
| 3. 评价 | 已提交 Observation、明确 Claim、相关实际帮助、兼容 Evidence | Evaluation 生成并校验 Evidence，再推断并校验 Belief 或明确保持原状态；所有语义结论来自真实模型调用 |
| 4. 决策 | 当前 Observation、Evaluation 结果、活动和权限、合法动作范围 | Policy 生成候选并接受独立执行记录下的语义校验；提交 Execute、NoIntervention 或 Defer |
| 5. 执行 | Exact ActionIntent、当前权限、有效通道、过期及语义前置条件 | 重验后派发获准内容；记录实际展示、明确未发生或结果未知 |
| 6. 收束 | 本轮决策、效果事实及待处理信号 | 更新实际帮助投影，记录完成或失败；确认在途效果已处理或隔离后才释放下一轮 |

各用途的上下文需包含判断所需的实际内容，不能只放引用标识。针对某次作答的提示、讲解及其语义校验必须能读取原题、相关原始作答、学习者请求和候选的完整拟展示内容；Evaluation 必须能读取相关 Observation、Claim 定义及实际帮助内容。校验器不能仅根据 Policy 自己的理由判断帮助程度。历史材料通过获准的精确引用装配，缺少必要来源时明确 non-resolution，不能以摘要猜测缺失的事实。

Observation、Evidence、Belief 和 Policy 各采用“生成一次、语义校验一次”的基础 Profile。普通完整轮次最多八次逻辑模型请求；若需要活动转换后重新进行 Policy 判断，再增加两次。真实模型可以判断某步无须改变正式认识，但测试脚本不能预写 Evidence 或 Belief 的结论。语义校验与生成使用不同 Execution 和固定规则，允许采用同一个模型；这不代表两个判断的错误相互独立。

在前述例子中，Observation 描述学习者提交的计算和请求，不决定该学习者已经掌握或不会某项知识。提示正式展示后，后续更正作答的 Evidence 需要同时读取原作答、实际提示和新作答，分别解释定位与重算对相关 Claim 的意义。只允许确定性程序做算术运算、精确引用、schema、版本与权限检查；“这句话是否在替学习者定位错误”仍由规则加 LLM 判断，不能通过关键词列表伪装成语义验证。

### 4.2 实际展示、活动转换与中断

浏览器按 Intent 中冻结的内容块显示纯文本，并确认实际已渲染的块标识、顺序、payload hash 和通道代次。完整确认产生相应发生记录，部分确认保留实际子集；这个边界只声称受控客户端确认渲染，不能声称学习者已经看见、理解或使用。没有确认时记录 Indeterminate，不能仅因超时写为 NotOccurred。

派发采用持久化待发送记录和固定 dispatch 标识。浏览器在同一通道内去重，重复确认不能重复计为帮助；重启后从服务端确认状态恢复。若浏览器本地状态与服务端记录不足以判明此前是否展示，则保留未知状态并对账，不自动重放内容以换取一个“成功”确认。实际显示与数据库不属于同一事务，本方案不承诺跨两者的物理 exactly-once。

主动中断或旧轮终止时，先关闭该轮后续提交和新派发资格。已经派发的内容必须完成确认，或由客户端确认旧通道停止并报告最后的已渲染块，再递增通道代次；旧代次的迟到命令不再产生新的展示。若无法取得停止或对账确认，该会话保持隔离，后续消息可以接收但不开始处理。经过一段时间本身不构成停止证明。新页面重新连接时必须先完成代次握手及旧派发对账，不能直接恢复排队消息。

撤权后禁止新的派发。撤权前已经发出的在途内容仍可能形成迟到发生事实，应保存当时的授权、派发和实际确认次序，并进入上述收束流程，不能改写为没有发生。该机制的成立范围是 Build 所控制的客户端与服务端；第三方渠道、离线客户端及任意不可信客户端的停止保证不由本轮证明。

诊断转教学使用独立的 Control Intent。活动转换由后端原子确认并形成 ActivityTransitionOccurred 后，才更新活动状态，重新装配上下文并生成教学 Policy。转换失败或结果未定时不开放讲解。普通 Hint 的展示确认不能充当活动转换成功；请求讲解也不能直接写成已接受帮助。

### 4.3 更正、重启和版本处理

学习者更正或有权管理者的纠正形成新事实及新修订。依赖旧 Observation 的 Evidence、Belief 和当前决策资格同步受到保护，随后分别由其 owner 重算。已经发生的帮助仍保留在历史中。Evaluation 对有帮助的作答作出有条件解释；系统不能为恢复一个“独立表现”标签而删除已有帮助。

进程恢复先读取持久状态，创建新的 worker 代次，拒绝旧 worker 的迟到提交，再逐项处理未完成工作。模型请求已发出但未保存响应时，该次输出为不可恢复；如预算和 Protocol 允许，另起 Execution，不能将新响应冒充历史响应。已提交未派发的 Intent 重新检查权限和前置条件；已派发结果未知的 Intent 走效果对账，不能盲目重发。检查点只提供恢复位置，不能补造正式认识或行动事实。

版本验证采用一个 Evaluation 规范变更：从已治理的 v1 切换到已治理的 v2，检查依赖该规范的 Evidence 和 Belief 当前性，再按新版本产生独立修订。版本内容提交与作用域激活是两个操作；测试管理者的授权绑定精确候选、基准版本和作用域。回退通过新的激活记录完成，历史 v1、v2 和原执行记录都保留。历史重建默认不调用模型，缺少材料如实报告 FULL、PARTIAL 或 UNAVAILABLE；重执行另建记录并按当前权限检查。

Evolution 在此阶段承接有来源的质量、校验和权限信号，保存待处置记录；不自动将某条日志提升为正式 SystemIssue，也不自动修改规范或提示词。问题归因和修订决定在 B5 报告中完成。完整自动治理平台、跨机恢复和复杂迁移编排属于后续能力。

## 5. 验证设计与判定方法

### 5.1 机制检查

机制组使用真实数据库、真实 owner 提交路径和真实客户端协议，模型边界可注入固定响应和故障。固定响应只用来控制触发位置，不证明模型具备理解或教学能力。每个编号下 A、B 是两个独立验收路径，共 24 条；每条在干净数据集执行一次并保留断言、记录和故障位置。一般程序错误可以修复后重跑受影响路径，原失败不删除；不因此新增真实模型批次。

| 编号 | A 路径 | B 路径 | 必须观察到的边界 |
| --- | --- | --- | --- |
| AVB-M01 正常分层 | 作答经过 Observation、Evidence、Belief、Policy | 无新表现的请求明确保持或不修订 Belief | 正式对象均由对应 owner 写入，来源可逐级追踪 |
| AVB-M02 校验与形式 | 必需语义校验 FAIL 或 UNRESOLVED | 错误 JSON、错引用或截断响应 | 候选不能提交；失败记录不冒充成功结果 |
| AVB-M03 权限 | 正文注入“管理员”或模型试图越权 | 有权正向操作及随后撤权 | 权限来自后端；撤权后不能新增获禁提交或派发 |
| AVB-M04 当前性 | 生成后、提交前更正关键输入 | 提交 Intent 后、派发前改变声明的执行前置条件 | 分别拒绝旧提交或记未发生，不换绑旧候选、不替换动作 |
| AVB-M05 串行与决策 | 处理中到达两条普通消息 | 分别执行 NoIntervention 和 Defer 子步骤 | 后续理解不抢跑；Defer 需新机会重判，故障不伪装成正常 outcome |
| AVB-M06 活动转换 | 转换确认后开始教学 Policy | 转换被拒或失败 | 只有真实转换打开教学上下文，不把请求或显示当作转换 |
| AVB-M07 实际帮助 | 提示完整展示及后续作答 | 只展示部分块及后续新题 | 来源记录实际内容；Claim-relative 解释不靠题目或 episode 标签清零 |
| AVB-M08 效果与中断 | 派发前取消并确认未发生 | 展示确认丢失，随后中断及停止对账 | 未知不冒充未发生；对账前不释放队列，旧通道不产生新效果 |
| AVB-M09 持久化恢复 | 候选尚未提交时终止进程并重启 | 原子提交后、派发前终止进程并重启 | 不补造候选，不重复正式提交；恢复后重新检查执行资格 |
| AVB-M10 去重与迟到 | 输入、提交响应及展示确认重复 | 已派发后进程重启并收到迟到确认 | occurrence 不重复；未知效果对账，不盲目重新展示 |
| AVB-M11 依赖传播 | 更正后重算 Evidence、Belief 并重新决策 | 分别建立 10、100、1000 个依赖节点后触发失效 | 先保护 current read/effect，再重算；未恢复分支不能沿用旧 revision |
| AVB-M12 版本与回放 | 治理提交、激活 v2、重新解释及回退 | 完整重建、缺材料和当前访问被拒三个子步骤 | 提交与激活分离；不改写历史，不使用旧权限绕过当前拒绝 |

24 条路径每条都有内部子断言，总断言数由实现生成，不将断言数宣传为独立场景数。真正的进程结束、重启和浏览器断连要在测试驱动中触发，不能仅调用一个名为 restart 的内存函数。AVB-M11 测量失效事务、阻止旧读和重算开销，固定候选的重算不产生真实模型成本；该结果只支持本地小规模依赖处理。

### 5.2 一次真实模型测量

B4 使用六个保留场景，每个四条学习者输入，共 24 个计划轮次。六个场景分别覆盖独立作答与自我解释、局部提示后更正、请求讲解并转换活动、部分展示后的继续作答、一次处理失败后的新请求、帮助后换同类新题。每条输入、允许的条件分支、预期观察点和结束条件在首次调用前冻结。各场景覆盖范围是预定的；如果模型没有选择相关动作，应记该路径未覆盖或教学选择缺陷，不能由测试驱动强制选择动作来冒充真实 Policy。

前五个场景中的后续作答及第六个场景的新题都用预先写好的合成输入。真实模型需要自行产生所有运行时语义判断，测试驱动仅扮演输入者和受控客户端。开发例子与保留样本使用不同题目实例和表达；既有 Spike 题目可用于开发，但不作为新的留出证据。保留样本在规范包和评分依据冻结后不用于调提示词。一旦据其结果修改规则或模型配置，原测量仍保留，新运行不再称为对同一留出集的独立首次验证。

另设 12 个独立校验探针，六个符合准则、六个有明确语义问题，直接调用冻结的语义校验器，各一次。探针分配为 Observation、Policy、Evaluation 各四个，每类两正两负，包含建议混入 Observation、实际提示与理由矛盾、忽略真实帮助而扩大能力结论等问题。它们用于测量误放、误拒和未决，不替代整条会话；探针标签及逐项理由不进入运行时输入。

会话完成记录与内容质量分开判断。一次轮次能够形成合法 NoIntervention、Defer 或有理由的 UNKNOWN，并不自动失败；但格式错误、必需校验未决后终止、或未到达该场景规定的结束点，不能算作完整成功。失败场景中被预先注入的那次失败用于验证恢复，不冒充一次模型错误；后续新请求必须实际走完原定路径。报告同时给出首次尝试结果和允许恢复后的结果。

### 5.3 质量评分和证据独立性

每个计划轮次按四项评分，各项为 0、1、2 分：是否忠实于材料，是否遵守本轮目的和帮助约束，是否正确说明实际帮助及相关 Claim 的证据意义，决策或评价理由是否与其实际内容一致。0 表示实质错误或本应产生的结果缺失，1 表示可用但有局限，2 表示满足该场景准则；总分至少 6 且无单项 0 才记为该轮内容可用。对合法无行动或证据不足的结果，评分仍检查其来源和理由，不因没有教学文字自动扣分。

运行中的语义校验通过率、离线内容评分和作者逐例审查分列。离线作者可以由负责实施的 Codex 完成，但必须明确它仍是模型辅助审查，不能称为独立人工盲评。测试驱动的计算真值能检查算术，不能证明“该提示保留了多少认知责任”。有争议的语义评分保留争议及原文，未解决的争议不计入正面质量支持；只有当它影响核心合同解释或 G2 决策时，才需要进一步专家判断。

语义误放率以有返回且可判定的负探针为分母，误拒率以有返回且可判定的正探针为分母；格式失败和 UNRESOLVED 单列，不能为了更好看的比率从计划覆盖中消失。六个正例、六个负例和六段会话只提供局部工程证据，不足以估计普遍可靠性，更不形成学习效果结论。若校验器误放一项而确定性提交合同正常执行，这是已知类型的语义质量缺陷；若未经所需校验、越权或引用失效状态仍提交，则是机制缺陷，处理等级不同。

### 5.4 测量指标

| 类别 | 报告指标 |
| --- | --- |
| 组合完成 | 六段会话及 24 轮的计划数、实际覆盖数、首次成功数、恢复后成功数、失败位置 |
| 模型质量 | 格式失败、语义误放、误拒、未决、四项内容评分；Observation、Policy、Evaluation 分开归因 |
| 响应时间 | 输入排队、上下文装配、每次模型请求、校验、数据库提交、展示确认、轮次收束的分段时间 |
| 状态成本 | 失效节点数、依赖深度、重算对象数、current 不可用时长、数据库大小、每轮记录数量与字节量 |
| 恢复能力 | 进程恢复耗时、未完成任务数、重复记录数、效果未知及隔离时长；是否需要操作员对账 |

延迟同时保留原始样本、中位数及样本分位数；24 轮的分位数不是生产 SLA。先以普通轮次中位数 15 秒、样本 P95 45 秒作为需要解释的工程警戒线，而非产品交互承诺。超过警戒线必须说明主要耗时来自模型链、上下文、重算还是展示等待，以及是否需要缩小能力或重新安排闭环；不得在未测量时通过并发同会话判断来缩短数字。

## 6. 预算、停止条件与 G2

### 6.1 运行前冻结和预算

本次只交付方案，不读取或展示密钥，不启动模型调用。后续实现使用既有 `DEERMIND_LLM_API_KEY`、`DEERMIND_LLM_BASE_URL` 和 `DEERMIND_LLM_MODEL` 配置约定，优先适配用户已选择的 DeepSeek 模型；实际 model 标识和 endpoint 以运行前核验为准，不假定名称能够自动映射到某个供应商版本。首次真实调用前告知用户所用配置类别和预算；只有配置缺失或不可用时才需要用户补充。

首次真实请求前固定代码、依赖、规范包、Prompt、Schema、Profile、样本、评分标准、模型标识、采样参数、输入输出限制及预算，并保存实际文件 hash；Git HEAD 不能替代未提交文件的 hash。候选生成与语义评审默认使用供应商支持的固定结构输出方式和温度 0，运行前核验相关参数，温度 0 不被解释为可重复性保证。预检失败形成配置或能力结论，不自动更换模型或输出方式后混用结果。

| 项目 | 首轮上限 | 计算口径 |
| --- | --- | --- |
| B2 预检和开发连通 | 40 次 HTTP 尝试 | 包括配置预检、极少闭环调试及这些调用的网络重试 |
| B3 机制检查 | 0 次真实模型请求 | 固定适配器测试；已有真实链路由 B2、B4 验证 |
| B4 六段会话 | 240 次基础逻辑请求 | 6 段 × 4 轮 × 每轮最多 10 次；实际无需调用的步骤不补满额度 |
| B4 语义或格式恢复储备 | 24 次逻辑请求 | 全批共用；一次重生成加重新校验消耗两次，每个边界最多恢复一次，每轮最多一组恢复 |
| B4 校验探针 | 12 次逻辑请求 | 六正六负，各一次；不自动修复探针候选或反复调用校验器 |
| B4 网络重试储备 | 24 次额外 HTTP 尝试 | 每个逻辑请求最多额外两次，全批仍受该储备约束 |
| 全阶段真实调用 | 340 次 HTTP 尝试 | 40 + 240 + 24 + 12 + 24；Build 程序发起的所有模型 API 请求均计入，没有另列免费评分批次 |
| 全阶段资源 | 输入 200 万 tokens、输出 50 万 tokens、费用人民币 50 元 | 任一上限先到即停止；这些是拟执行上限，不是预计用量或充值授权 |
| B4 执行时间 | 活跃运行累计 90 分钟 | 包括请求、退避和受控客户端等待；不包含编码、人工审查和已记录的网络暂停 |

一次正常轮次最多十次基础请求，加一组允许的生成与校验恢复最多十二次，网络重试另计 HTTP 尝试。全局储备不足时不再开始恢复。Probe 不走候选重生成路径；模型没有接受负探针的能力也不能通过反复抽样消除。一次会话失败后仍可运行其他预定会话，以获得既定范围的证据，但不能新增第七段来替换失败。

单次 HTTP 尝试超时为 60 秒，允许的两次网络重试分别退避 1 秒和 3 秒。受控客户端正常展示确认等待 15 秒，超过后转入未知效果对账；验证驱动为一次对账预留 30 秒，仍未确认则记录隔离结果并结束该测试步骤，不在应用中释放受影响队列。计时结束、测试步骤结束与业务轮次已经安全收束是三个不同状态。

输入预算按模型实际 tokenizer 或可证明保守的上界执行；单请求语义输入暂定不超过 16,000 tokens，输出上限 8,192 tokens，本地序列化请求保护上限 200,000 字符。准备阶段检查所有冻结输入及正常增长路径，预算不足就明确失败，不能偷偷删减原作答或实际帮助来源。若供应商约束不同，需在批次开始前调整并重新冻结；运行中不能静默截断或变更参数。

费用计算必须基于实际配置供应商及对应模型的可核验单价，记录日期、币种和换算依据。发送前为输入上界和允许输出预留成本，超时且 usage 未知的调用按保守上界计入；获得实际 usage 后据实核对。人民币 50 元是此方案的费用保护上限，不是模型报价。尚未取得可靠计价或上界时，真实批次不启动，本地实现和机制检查仍可继续。

### 6.2 网络失败、工程缺陷与架构问题

网络超时、连接中断和供应商暂时不可用单独记为传输失败，可以在同一冻结配置下重试；每次尝试使用独立 attempt 标识并关联同一逻辑请求。收到无效 JSON、语义校验失败或必需结果未决属于输出或语义失败，不能改标成网络问题。原失败、恢复请求和最终结果均保留，首次成功率与恢复后成功率分别计算。

连续三次传输失败暂停真实批次并保存进度，避免在网络故障中消耗剩余预算。网络恢复后只继续未完成的计划位置，不重跑已完成正例。未能获得响应的计划项标为传输阻塞，不计入语义错误分母；它们仍影响证据覆盖是否足以作结论。如果本轮无法取得足够有效覆盖，报告 INCONCLUSIVE 或 G2 HOLD，不能把网络问题判为架构被否定，也不能用剩余样本伪称完成全部验证。

| 问题类型 | 处置 | 能否继续其他工作 |
| --- | --- | --- |
| 普通实现缺陷 | 修复事务、引用、序列化或适配错误，重跑受影响机制路径；保留旧失败 | 可以继续不受影响的工作；真实批次中改变执行语义后需分开版本，不能合并成绩 |
| 语义质量缺陷 | 保存原输入输出、校验意见和影响，计入既定测量 | 在权限与状态边界完整时继续剩余预定样本；本轮不自动开展提示词调优竞赛 |
| 核心机制违约 | 停止依赖该边界的验证，分析是否可在现有合同内修复 | 可以检查独立部分，但不得以机制测试 PASS、LLM 失败率低等理由掩盖该问题 |
| 现有设计无法实现 | 明确冲突的 owner、权限、因果或一致性合同，形成设计修订建议 | 返回相应设计层；不继续无关抽样，不在实现中绕过合同 |
| 预算或时间耗尽 | 输出已覆盖、未覆盖和当前结论 | 结束本轮；新增批次需先有独立原因、计划和预算 |

同一根因经过一次完整修复及针对性验证仍无法在现有合同内收束时，应给出阻塞分析和可选修订，不以相似小补丁无限延长工作。该规则是停止自动修补的条件，不代表一次实现失败就否定整体设计。若真实批次因实现缺陷使某段证据失效，本轮如实报告，不能默默删除并更换样本。

### 6.3 G2 的判断

G2 的机制条件是 24 条预定机制路径全部实际执行并通过必要断言，不存在未修复的核心违约，并且真实系统确实展示了从输入到 Evaluation、Policy、实际效果及后续决策的组合路径。固定模型响应下的恢复、权限和事务测试可以证明相应工程机制，但不能独自满足真实闭环条件。版本切换、更正、历史重建和进程恢复需要实际执行记录，不以代码存在代替验证。

本轮另外设置两个进入 MVP Definition 的局部工程筛选条件：六段真实会话至少四段完成各自四轮的预定路径，其中至少一段含真实帮助及后续评价、一段含独立作答及后续决策；24 个计划轮次中至少 18 个达到 §5.3 的内容可用评分。对事先声明的故障注入轮次，按是否正确终止并保留原因评分，不能把该例的故障本身当作模型质量错误。这些数值是本方案选择的有限样本门槛，尚无统计校准，也不是对产品质量的承诺。

通过上述条件仍需解释延迟、复杂度、观察与审计成本、重算行为及已知缺陷。语义探针发生误放不会自动否定修订后的架构，但必须进入缺陷清单和使用限制；若错误说明当前实现实际上无法满足选定场景的关键语义，即使总分达标也不能宣告该能力可用。未达筛选条件时给出明确修订、能力收窄或 G2 HOLD，不在本轮反复调优直到数字达标。能力收窄若改变预定支持声明，应作为新决定说明，不能追溯修改原门槛。

最终报告使用 G2 PASS、HOLD 或 DESIGN REVISION REQUIRED 表示阶段决定，并保留每个工作项自己的结果。PASS 只支持在已知能力和成本下定义 MVP；它不表示具备无人监督教学能力、已经证明学习效果或可以进入真实儿童 Pilot。核心合同只能在正式设计修订后改变，不能作为普通“后续优化”搁置。

## 7. 工作顺序与交付管理

| 工作项 | 依赖 | 具体交付与完成条件 |
| --- | --- | --- |
| B1 组件与验证方案 | v1.0 系统设计及 Phase 6 评审 | 本文给出实现方案、24 条机制路径、真实测量范围、预算及 G2 条件；文件交付不代表已经实现 |
| B2 最小真实闭环 | B1 | 建立工程、数据库 schema、规范包、Protocol、适配器及客户端；先通过离线主链，再在 40 次尝试内留下最小真实闭环记录；冻结保留样本和运行参数 |
| B3 组合与恢复验证 | B2 的持久化、提交和展示路径 | 执行 AVB-M01–M12 的 24 条路径，修复可定位缺陷；核心机制阻塞未解决时不启动依赖它的 B4 |
| B4 质量与成本测量 | B2 真实链可运行，B3 核心机制无阻塞 | 按唯一冻结配置执行六段会话和 12 个探针，完成逐例评分与成本归因；达到停止条件即收口 |
| B5 报告与阶段评审 | B2–B4 的实际证据，允许其中有失败或未覆盖 | 输出统一 Build Validation Report、G2 判断、明确后续工作；需要修订时把问题交回正确设计层 |

主文档统一放在 `doc/system-design/build/`，同一文档只保留最新版本。当前只有本方案，最终增加一份 `DeerMind_Architecture_Validation_Build_Report`；实施中直接维护代码、配置、测试和结构化运行证据，不为每次修复另外创建叙事文档。只有确实改变上位合同的决定才修改相应设计并记录 ADR，不能把实现日志堆进设计基线。

后续原始执行材料放在 `src/architecture_validation/` 下的 fixtures、protocols、runs 和 reports 中；每批清单固定输入与代码 hash，保存请求、返回、正式提交、效果确认、预算账和评分依据。各次运行使用新目录，历史记录不覆盖，凭据和授权头不进入证据。Build 证据不要求把全部 Spike 历史包作为启动依赖；旧 Spike 仍通过其自身索引保留实验结论。

阶段报告至少回答五个问题：实际做了什么；哪些机制及场景已有证据；哪些错误属于模型判断、工程实现或设计冲突；一次完整交互需要多少调用、等待和维护成本；是否满足 G2、后续哪些能力可用以及哪些必须保留限制。工作完成以这些问题有明确答案为准，不能以测试轮数增长代替进展。

本方案的所有执行预算均从后续首次真实调用开始记账。当前交付之后的直接工作是 B2；B2 可以自主完成工程搭建与离线验证，需要模型配置时沿既有约定核验并通知，不以重新开展 Spike 调优为前置条件。
