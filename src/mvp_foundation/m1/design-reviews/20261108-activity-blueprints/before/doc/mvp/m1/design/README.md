## 2. 用一个功能说明分工

| 同一功能：检测中求助 | 应写清什么 |
| --- | --- |
| PRD | 实质求助先结束当前检测轮，再由检测活动建立讲解／答疑子活动；已提交表现和实际帮助保留，未做题不判错 |
| 交互规格及原型 | 求助入口、轮结束告知、如何在同一对话建立子活动、哪里查看已提交题及本次结果；正常完成、轮后答疑与提前结束如何不同 |
| 内容与模型规格 | 本例题面、解法、参考答案、受助与无当题帮助的判据；检测活动、检测轮和帮助后新题如何影响Evidence，哪些结论不能推断 |
| 工程设计 | 请求、记录、串行、中断和模型调用如何实现，怎样保证规定的帮助与评价顺序 |

例如“求助结束当前检测轮并取消原题单未开始轮次”只在PRD维护完整业务规则，详规引用并展开表现；“增加四分之一”的两题及七天标准只在内容规格§4.10完整维护，PRD引用其适用范围。若详规与PRD矛盾，应定位并修正，不能让实现者任选一份。涉及通用模型责任的矛盾，还须同步其上位定义。

## 3. 同步推进与接收

先有场景和范围草稿，再同时展开规则、实际内容和交互；原型暴露的输入、反馈或状态缺口可以修改PRD，内容例子暴露的模型缺口可以修改详细规格及上位合同。这里的同步指交替核对和共同完成，不要求每次编辑都改动所有文件。

每包沿现有文档补充，不额外建立一份PRD。步骤应有编号、原型位置与对应截图；同一画面支撑多步时明确关联。数据使用mock，保持教学与评价逻辑一致；不要求接LLM或实现所有菜单之间的数据持久化。

共同完成条件、状态与评审记录位置统一见[M1工作计划](../README.md#4-每包的推进与完成判断)。原型方案已有授权的继续执行；新业务决定或尚未确认的界面调整先形成具体方案再请用户确认。后续正文、页面或mock变化时，同批检查截图，不将旧截图冒充新状态。
