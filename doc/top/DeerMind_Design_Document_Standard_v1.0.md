## 1. 目的与适用原则

文档应使没有参与历史讨论的读者理解：要解决什么问题，为什么选择当前方案，具体行为或机制怎样成立，哪些边界必须遵守，以及下一步可以凭什么继续。专业性来自可核对的事实、连贯的推理和明确的责任，不来自术语、表格、公式或章节的数量。正文负责建立整体认识并解释重要选择，索引与附录负责完整查找；两者不能相互替代。

本规范同时适用于产品和技术交付，但不要求它们采用同一套章节。产品需求必须说清业务行为，架构设计必须说清职责和机制，验证报告必须呈现真实证据。各类型的最低内容要求见 §3，项目阶段、交付物数量及 Gate 仍由路线图规定。文档目录或章节大纲已经建立，不表示内容、资产或阶段已经完成。

“必须”“不得”表示交付约束；“建议”“通常”表示可依文档目的裁剪的写作方法。没有适用对象的要求可以注明不适用及理由，不必制造占位章节。文档头、真实状态、依据可追溯、职责不越界和完成声明有证据是共同要求，不能以文档简短或尚在起草为由省略。

本次维护修订沿用既有文件名和 v1.0 标识，保留原有写作原则；具体内容通过修订日期和 Git 区分。原规范过度依赖架构文档模板、没有明确统一文档头，并要求在本地保留旧版，已不适应现行产品交付和 Git 维护方式。本次修正这些问题，也合并重复条款和装饰性公式。旧修订及已冻结实验的依据继续按其原始记录查阅，不反写历史评审结果。

## 2. 文档头与状态表达

每份正式维护的文档在一级标题后设置统一的引用块文档头，以 `> **字段**：内容<br>` 逐行呈现；最后一行不必加 `<br>`。不再用“元信息表”、正文散句或标题里的版本号代替文档头。中文标题已经完整表达名称时，无需再重复中文名称；英文标题须补中文名称。文档头后以分隔线进入正文，元信息不占一个正文章节。

| 字段 | 填写要求 |
| --- | --- |
| 文档性质 | 说明是产品定义、需求规格、概念设计、工程设计、验证方案、结果报告、评审记录还是管理文件；所属阶段适用时一起注明 |
| 版本 | 有发布版本则准确填写；未发布文档可写“工作稿，修订由 Git 追溯，尚无批准基线”，不能虚构正式版本或批准 |
| 状态 | 分别说明大纲、内容草案、待评审或已批准的成熟度；涉及阶段时说明实际 Gate 状态。历史参考和被替代文档须明确标识 |
| 上游依据与基线 | 链接实际依据的文档，标明准确基线或“工作修订，尚未冻结”；依赖较多时引用正文中的输入清单。批准交接时按 §6 固定内容 |
| 写作规范 | 链接本规范及适用的项目共同规则；规范自身不必引用自身 |
| 维护责任 | 填实际责任人或责任角色；未分配的后续责任明确待指定，不能把本次代为整理等同于永久承担 |
| 评审记录 | 区分作者自检、用户决定与实际评审；可以链接集中记录。没有评审就写未评审，不以工作授权冒充批准 |
| 更新日期 | 使用实际修改日期，格式为 YYYY-MM-DD；需要时另列创建日期 |
| 修订说明 | 说明本次主要变化、原因及是否涉及范围、模型语义、验收指标或下游交接；不在每份文档复制长篇讨论历史 |

README 等导航文件可以使用精简文档头，至少包含文档性质、当前状态、维护责任、规范链接和更新日期，并链接权威的版本及阶段记录。研究或评审文件可以补充检查范围、输入快照和用途。字段可以按阅读顺序组织，但不得把版本、内容成熟度和 Gate 结论混写为一个无法核对的“已完成”。

文档头只声明文档实际具备的内容与依据。大纲仍写大纲，尚未准备的资产仍写待准备，未决定事项在正文及登记位置可查。模板提示在填充相关正文时替换掉；保留大纲的章节则明确交付要求，不伪装成已经存在的方案。文档状态变化必须有实际完成或评审依据，单纯补齐格式不提升成熟度。

## 3. 文档职责与交付内容

文档划分以读者要做出的判断和下游需要接收的内容为依据，不能仅按技术层级或文件数量划分。开头应以简明正文说明本文解决的问题、输入、输出、直接接收者和接收条件；同时说明本层不决定什么。复杂文件可将依赖清单单列，但不必在多个开场段落重复“职责”“目标”和“输入输出”。

| 文档类型 | 必须交付的核心内容 | 不得混同的事项 |
| --- | --- | --- |
| 产品定义与路线图 | 用户与现实情境、依据及其限制、需求价值与取舍、完整范围、阶段目标、可行性前提和待决事项 | 想法不等于已证实需求；工程增量不自动缩减完整产品范围 |
| 需求与验收规格 | 产品对象和关系、按角色展开的具体功能与业务过程、状态和规则、权限与 AI 行为边界、异常及非功能要求、可检查的验收场景 | 用户故事和需求索引不能代替业务逻辑；接口、存储或页面排版不替上游补定产品含义 |
| 概念架构与 Space 设计 | 核心问题、整体结构、对象语义、责任及事实归属、生命周期、跨空间合同、不可违反的边界和重要取舍 | 实现便利不能反向改变语义所有权；个人事实、解释、判断和指令不能混用 |
| 产品交互、领域内容与数据权限设计 | 可走查的操作与反馈、实际领域或内容材料及质量依据、身份授权与数据生命周期；各自交付真实资产及接收合同 | 原型不等于真实模型能力；统一打包不改变各 Space 的语义归属；下游设计不静默覆盖需求 |
| 系统、工程、协议与组件设计 | 运行机制、接口与状态、数据及版本一致性、失败恢复、观测与维护、技术取舍及检查方法；细节按所属层级展开 | 机制说明不冒充已执行证据；分期实现不把语义不变量降为可选项 |
| 验证方案、资产规格与结果报告 | 方案定义问题、指标和测量方法；资产规格索引实际案例与参考；报告呈现配置、执行、结果、失败及结论边界 | 计划、脚本存在、实际运行、质量达标和产品价值是不同结论，不能互相替代 |
| 实施计划、交付、治理与 Gate 记录 | 计划说明依赖及退出条件；交付说明实际软件和操作证据；治理维护决定与变更；Gate 记录引用被评审基线作出阶段判断 | 被评审对象不自行授予阶段通过；交付清单不替代实际产物 |

需求规格应使读者在没有原型时也能理解产品如何工作。关键功能从“谁在什么情境下，希望得到什么结果”开始，接着解释前提、输入、正常过程、结果与状态变化、业务规则及关键例外，最后关联验收场景。不强制每项功能机械使用同一张卡片，但这些信息不能缺失。后台必须具体说明可查看什么数据、如何关联、允许哪些维护操作及其影响，不能用“支持管理”“完整可追溯”等词代替功能定义。

架构文档先建立整体职责图景，再说明少量典型运行过程和边界；协议或组件文档承接详细字段、算法和操作合同。需求规格则应覆盖其承诺范围内的主要业务分支，不能误用“架构只讲典型路径”作为遗漏功能的理由。概念层不提前固定数据库或调用协议，实现层也不能把单写责任、权限、证据条件或版本失效等上位语义当作自由选择。

验证方案应把指标、分母、参考依据、判定条件、适用节点、有限投入和停止规则说清楚。尚无基线的阈值可以标为待校准，同时明确何时校准、依据和决定责任，不能先运行再按结果改门槛。结果报告区分实现缺陷、传输故障、语义判断错误与有效未决，并保留实际输入输出、配置和来源的可追溯位置。有限样本支持什么结论、不能支持什么结论必须与证据匹配。

## 4. 从问题到结论的正文组织

正文先说明问题与约束，再给出整体产品或系统图景，随后展开关键行为、责任、运行过程和接口边界，解释重要取舍，最后说明风险、未决与交接。这个顺序是一条论证路径，不是统一的八章模板。既有项目大纲可以沿用；只有当章节不再承担清楚的职责时才调整结构，并同步引用。

重要选择要写清依据和推理。事实说明来源，假设说明尚缺什么证据，已确认决定说明适用条件，待验证结论说明验证责任与节点。这些区别应融入相关段落或表格，避免只在文档顶部挂一个“待验证”标签却让全文使用确定语气。对长期影响范围、权限、责任、数据含义或扩展性的选择，还应解释真正考虑过的替代方案、当前代价及重开条件；不要求每个日常实现细节另写决策记录。

抽象概念应有足够小的现实例子，说明对象、关系和结果如何对应。例子用于检验定义，不能悄悄扩充正式范围。例如，系统展示过一道题的解法，只能证明发生过帮助；后续学生的实际表现还需按独立或受助条件解释，不能因讲解结束就声称掌握。合成例子与真实观察须明确区分。

不变量应长期有效、实现必须遵守、违反后会破坏系统语义，并能够被审查或验证；当前偏好不能包装成不变量。跨模块或 Space 的合同要能回答谁产生、谁读取、谁能修改、权威依据在哪里、版本如何绑定、失效如何传播和权限到哪里终止。正文解释核心边界，完整规则可放相应章节或附录，不把几十条规则置于同等叙事地位。

未决事项区分概念、经验验证、实现和治理问题，记录影响、现有依据、负责阶段和最迟决定节点。未知或当前无法判定可以是合法结论，但不能借此省略下游开工所需的决定。风险应描述可识别的失败情形、触发条件、后果和处理方式，不能仅写“模型不准确”“系统复杂”。涉及新的产品取舍或关键语义变化时提出讨论；文档整理不替用户作出这些决定。

## 5. 语言、层级与图表

采用现代工程中文，以完整、连贯的段落解释问题。一个段落围绕一个中心意思展开，相关的几句话应相互承接；不把每句另起一段，也不将多个无关主题挤在一个长段落中。段落长度服务于理解，不规定固定句数或字数。优先写清行动者、对象、条件和结果，避免翻译腔、口号、含混的“支持”“赋能”以及无必要的中英混排。

正式概念首次出现时对齐中英文，后续使用稳定名称；代码标识、模型对象和协议名可保留英文。普通概念不另造专有词。术语由其权威文档定义，下游引用并补充本层含义，不建立相似但不一致的第二套定义。

标题通常控制在“文档标题—章—节”三个层级。每个标题承担完整的阅读任务，不为每个术语设置小节；复杂内容先调整信息组织，再考虑增加层级。主题和篇幅决定章节数量，不强制所有文件八章，也不要求所有文档以总结重述全文。

列表用于真正并列的选项、步骤或检查项。表格适合比较、状态、权限、编号索引、验收及追溯等结构化信息；这些表格可以是正式正文的一部分，不必机械移入附录。表格单元格过长、包含多个论证过程时，应先在正文解释，再用简洁摘要与章节链接组织查找。同一业务规则保持一个详细维护位置，其他位置保留必要摘要或引用，不能不断复制完整段落。

图示应回答一个明确问题，例如对象关系、状态变化或跨角色流程。图中对象和箭头与正文术语一致，配以必要解释；Mermaid 应检查语法及实际图意，渲染检查与语义检查分开记录。不能只凭图形美观判断设计成立。公式仅用于需要精确定义的关系、约束或计算，不用数学框线装饰普通主张。

历史讨论、废弃方案的详细过程和完整字段清单可放在附录、已存在的评审文件或资产中，通过链接进入。必要的决策理由、行为边界和未决影响仍须留在正文。文档应当能独立阅读，但独立阅读不意味着复制所有上游内容。

## 6. 版本、引用与资产追溯

`doc/` 中维护现行版本，历史修订通过 Git 查阅，不默认并列保存多个版本文件。已明确作为参考的 `mvp/archive/` 保留其历史用途；`src/spike/` 等验证目录可以保留实验需要的冻结快照，不属于现行设计文档。不得为了统一格式改写已冻结输入、原始报告或历史通过记录。替换现行文件前，应确认被替代内容已有可恢复历史，并处理所有现行引用。

工作稿不必每次修改都升级发布版本或改名。稳定文件名与版本化文件名均可沿用项目约定；发布新的正式文档版本时，须说明改变了什么、为什么改变、是否影响语义及下游。语言重写、结构整理与语义变更分别说明，不能以“仅整理”为名改变范围、权利或验收标准。同一标称版本内的维护修订使用 Git 提交或可恢复快照确定准确内容，不能只凭日期识别冻结基线。

当前文档之间优先采用相对 Markdown 链接，必要时链接章节，并保留稳定编号。仅写“见最新设计”不足以建立正式依据。批准交接时记录准确提交、文件与资产版本；工作区有未提交变化时，HEAD 不能代表全部输入，应先建立可恢复的评审快照。标签可用于导航，但不能移动旧标签改写原批准内容。未入 Git 的资产需登记位置、版本和校验信息，敏感资料通过受控索引引用。

共享内容指定唯一维护位置：产品行为在需求中定义，测量指标在验证方案中维护，跨阶段决定在登记册记录，实际结果在报告中保存。下游引用对应编号并增加实现或证据，不再维护一套数值或决定。追溯需要能从需求找到设计、资产、实现和结果，也能从失败回到相关要求；以实际需要建立关联，不能为了编号齐全制造不存在的资产。

原型、领域包、案例、源码、配置和运行记录都是独立资产。说明书列出预期清单并不证明它们存在；资产存在也不证明审查、导入或执行成功。交接记录分别给出实际位置、版本、就绪情况与相应证据，缺项如实标明，不用未来时的计划冒充完成记录。

## 7. 编写与变更流程

开始编写前，先读适用规范、上游基线和当前决定，确认本文的读者、职责及直接交接对象。若规范与实际文档类型不适配，先修改共同规范并说明理由，再修改受影响文档；不能各文件自行发明例外，也不能为了满足模板强行更改产品或模型。

新建文件先设文档头和必要结构，再按依赖填充内容。需求从依据与业务目标推导，设计从已明确的产品和语义约束推导，报告从实际执行记录推导。尚未成立的部分标明状态、影响和后续处理位置，不依靠作者临场解释才能理解。完成一节时删除已被正文取代的模板提示，保留仍有效的未决事项。

修改既有文件时先识别变化属于表达整理、内容细化还是实际决策变更，再检查关联的定义、图表、规则、引用、验收和资产说明。应重写相关叙事以保持完整，不能只在末尾追加一条新规则而让旧正文继续矛盾。涉及新决定时先取得必要决定，再在唯一维护位置更新并传导；常规错字、标题、文档头和链接修复可直接处理。

提交交接前完成 §8 的检查，说明本次检查的范围、证据、剩余问题及内容成熟度。检查结果使用现有文档的完成条件、共同记录或交付说明承载，不为每次格式修订新增一份长期报告。作者自检与其他人审查明确区分，但不强制小团队增加第二位管理员或为日常编辑设置新的批准流程。

## 8. 审查与完成判断

文档审查分为形式与内容两个层面。链接、编号、表格结构和文件存在性可以自动核对；论证是否成立、功能是否具体、语义是否一致以及证据是否支持结论必须直接阅读判断。机械检查通过不能表述为“已全面符合规范”，写作质量合格也不能表述为产品、模型或 Gate 已经通过。

**形式与可追溯性检查：**

- [ ] 文档头具备适用字段，版本、状态、责任、日期和评审情况真实一致。
- [ ] 本地链接、章节引用、编号与资产位置有效，标题和术语一致。
- [ ] 现行文件与历史参考可区分，冻结依据能够恢复；未提交内容未被错误归入旧提交。
- [ ] 图表和 Markdown 结构可阅读，模板提示与实际正文状态相符。

**内容与交接检查：**

- [ ] 读者在开篇能理解本文解决的问题及整体产品或系统图景，正文有连贯的解释而非索引堆积。
- [ ] 关键功能、责任、状态变化和例外具体；重要选择说明依据、取舍与适用条件。
- [ ] 事实、假设、决定和未决可区分；未决影响及处理节点明确，没有未经决定的范围或语义变更。
- [ ] 跨文档职责和权威来源一致；重复摘要不产生第二套规则，语义合同与权限边界未被下游绕过。
- [ ] 输入、输出、接收者及完成条件清楚；本文职责内的必要内容没有无理由推给后续阶段。
- [ ] 实际资产和结果有相应证据，有限验证的适用范围表达准确；内容完成、资产就绪、运行达标与阶段批准分别判断。

这些清单是审查标准，不是本规范对其他文档的通过声明。实际检查可在适用交付中记录“通过、待补、不适用”及依据；发现问题时回到对应内容修正。最终交接质量取决于接收者能否在清楚、真实、可核对的输入上继续工作。
