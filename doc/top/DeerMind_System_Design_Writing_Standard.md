# DeerMind 系统设计文档规范

> **版本**：v1.0<br>
> **状态**：首版规范，待用户审阅<br>
> **维护与评审**：Codex 编写及自检，用户审阅<br>
> **更新日期**：2026-11-11<br>
> **修订说明**：按 SwDD 内容要求及技术写作指南重新建立工程专用规范；见[本轮记录](../mvp/DECISIONS.md#32-swdd规范与工程文档重建)。

本规范用于 M1 及后续版本的系统总体设计、模块详细设计和技术支撑设计。目标是让实现者知道程序如何工作，并能据此编写正常路径和关键异常的测试。产品需求、原型和研究报告继续使用各自的组织方式。

## 1. 依据与适用方式

| 依据 | 采用的内容 | 适用限制 |
| --- | --- | --- |
| [NASA SwDD（Software Design Description），Ver D](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695674/5.13%2B-%2BSwDD%2B-%2BSoftware%2BDesign%2BDescription) | 架构、组件、算法、数据结构、输入输出、执行过程、接口、取舍与追溯；其他位置已有内容可引用 | 作为内容依据，不照搬航天项目的审批和安全等级要求 |
| [NASA SWE-058：Detailed Design，Ver D](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695443/SWE-058%2B-%2BDetailed%2BDesign?desktop=true&macroName=content-reporter) | 设计应支持编码、编译和测试，避免实现者再对关键机制做重大解释 | 不要求预先展开所有函数或逐行写出代码 |
| [Google：Clear sentences](https://developers.google.com/tech-writing/one/clear-sentences) | 明确行动主体、使用具体动词、以事实替代模糊评价 | 应用于中文技术表达，不机械套用英文语法或字数规则 |
| [Google：Lists and tables](https://developers.google.com/tech-writing/one/lists-and-tables) | 顺序过程用编号；并列内容用列表；比较和结构化数据用表格 | 表格不承载长篇推导，不把所有正文改成项目符号 |
| [C4：Notation](https://c4model.com/diagrams/notation)与[图示检查表](https://c4model.com/diagrams/checklist) | 图的名称、范围、元素、连线含义及图例明确 | 用于架构图的表达质量，不代替接口、算法或生命周期设计 |

以上资料于 2026-11-11 核验。本文是项目裁剪规范，不宣称获得 NASA 认证或逐条符合其完整工程制度。SwDD 没有规定中文文风、Markdown 格式或九份文件划分；下文的目录、文档头、AI 合同、校验方式和升版规则是 DeerMind 的项目约定。

对工程文档，本文替代[原通用规范](DeerMind_Design_Document_Standard_v1.1.md)的正文组织和文档头要求；继续保留逐批升版、可追溯来源及真实记录评审结论的原则。旧规范及其他类型文档不随本次重建改写。

## 2. 文档组织与内容归属

总体设计描述系统边界、分层、模块关系、运行进程和跨模块协作。详细设计按实现责任和数据所有权划分，每个模块集中说明接口、数据、处理、异常和验证。M1 的九份文档及章节范围以[工程入口](../mvp/m1/engineering/README.md#1-文档分工)为准；文件数量是项目选择，不是 SwDD 要求。

- 产品规则引用 PRD 或产品规格的具体章节，正文接着说明实现方法。不能再次写一遍产品概念作为模块设计。
- 模块维护自己的操作、数据表和事件载荷。共用事件信封、任务执行、授权机制在公共运行设计中定义。
- 跨模块流程在总体设计说明交接；模块内部步骤在模块详细设计展开。总体设计不复制字段表。
- AI 底座说明模型、工具、上下文和记忆机制；具体 Agent 的用途、取材限制和输出含义归其业务模块。
- 客户端说明组件、状态、渲染和接口接线，引用交互规格与原型。部署设计说明实际环境与适配方式。
- 一个事实或合同只完整维护一次。引用应直接指向接口、图或章节，避免读者连续跳转才能找到定义。

新文档从已确认需求、当前约束和工程问题出发编写。归档稿只用于识别问题和比较方案；不得复制段落、重排旧章节或将旧候选技术作为已批准设计迁入。确需重新采用某个旧建议时，在对应设计中重新说明理由并提交审阅。

## 3. 语言风格

### 3.1 句子写出可落实的行为

1. 先写结论或操作，再说明原因。一个段落围绕一个问题展开。
2. 明确执行者，优先使用“教材模块保存候选”“Evaluation 校验资格”等主谓结构。跨模块段落不用含糊的“系统处理”。
3. 条件在前、结果在后。多个条件写成条件表或分支，不用连续分号串成一段。
4. 使用具体动词：读取、校验、拒绝、写入、返回、等待、重试。概述可以使用“负责”“支持”，详细设计必须继续说明做法。
5. 描述设计行为使用直接陈述。事实、建议、假设和未决分别标明；草案身份在文档头声明，具体候选在相应选择处标明，不在每段重复“尚未实现”。
6. “及时”“可靠”“合理”“统一”“完整”等词不能代替条件和机制。涉及数值时给出单位、范围和依据；未知数值列为待定，不凭写作需要编一个值。
7. 去掉“本章将介绍”“需要说明的是”等无信息开场。章节标题直接说明对象或问题。

以下仅演示表达形式，不决定 DeerMind 的具体实现：

| 不能独立支撑实现的写法 | 应写出的信息 |
| --- | --- |
| 系统确保任务可靠恢复 | 哪个模块保存恢复位置、保存何时完成、谁触发恢复、恢复读取什么、重复触发如何处理 |
| 通过统一协议实现跨模块协同 | 调用方、被调用操作、输入输出、同步或异步方式、失败返回以及各方写入的数据 |
| 自动更新学生状态 | 哪个操作接收什么 Evidence、先做哪些资格检查、调用哪个计算函数、何时提交结果和事件 |

正文不以口号、原则和否定清单为主体。约束紧邻受约束的操作，取舍紧邻所选方案，说明其实际影响。

### 3.2 术语与规范性用词

同一对象使用同一名称。首次出现写中文名及英文标识；后续沿用。文件名、字段名、函数名、状态值使用代码格式，不能用几个近义词交替指代同一状态。

“任务”须区分领域 Task、学习活动和后台执行任务；“实例”须指出是题目内容、活动实例还是 Agent 执行实例。只有发生歧义的位置需要补足类型，不在每页重复术语表。

| 用词 | 本项目含义 |
| --- | --- |
| 必须／不得 | 已确认的约束，或本规范的强制检查项；具体设计标明依据 |
| 建议 | 待选择或可权衡的方案，说明理由和代价 |
| 可以 | 允许的行为或可选实现，说明启用条件 |
| 待定 | 缺少决定或证据；写明影响和关闭条件 |

“已实现”“测试通过”“已验证”只描述有实际结果的事实。设计预期和试验假设不能使用这些措辞。

## 4. 表达方式

| 要表达的信息 | 首选形式 | 必须说明什么 |
| --- | --- | --- |
| 设计理由与权衡 | 简短段落，必要时对比表 | 当前问题、候选差异、选择及代价 |
| 并列约束或能力 | 无序列表 | 同层级、相互独立的条目 |
| 执行步骤 | 编号列表或时序图 | 起点、顺序、处理者、结果；分支另列 |
| 字段与接口参数 | 表格及 Schema | 类型、必填、约束、缺省及空值含义 |
| 输入输出样例 | 带语言标识的代码块 | 合法结构、样例身份、与正式合同的对应 |
| 条件分支 | 决策表 | 条件、动作、输出；条件重叠或均不满足时的处理 |
| 生命周期 | 状态图或状态迁移表 | 初始与终止状态、触发者、守卫条件、非法转移 |
| 模块关系与部署 | 架构图、部署图 | 边界、依赖方向、进程及外部服务 |
| 计算逻辑 | 公式或伪代码及算例 | 变量、输入域、分支、边界、精度和输出 |

一个表格集中表达一种关系。单元格需要分段解释时，拆成正文或子节；不把完整流程塞进“说明”一列。列表前给必要上下文，列表项不混合规则、历史和评审记录。

图和文字互补：图表达结构与顺序，文字说明图中无法读出的条件和数据变化。截图用于证明交互对应，不能替代后端设计；同一内容无需同时重复为图、表和长段落。

## 5. 详细设计的最低信息

各模块按实际复杂度展开以下信息，可以在操作小节中集中说明，也可以引用本模块的公共数据定义。无需为每个简单函数机械建立整套子标题。

### 5.1 操作与接口

重要操作须说明调用者、前提、输入、处理顺序、输出和失败结果。HTTP、内部函数、异步消息和工具调用分别写清交互方式，不只列一个名称。

字段表至少包含名称、类型、必填性、含义和约束；按需补枚举、单位、默认值、空值与未知的区别。接口给出代表性请求和响应，说明权限、可观察副作用和错误。涉及重试时写清重复请求如何识别及返回；涉及分页或流式结果时写清游标、顺序和完成条件。

Schema 或可执行合同建立后，应成为相应字段的唯一完整定义，设计文档引用它并解释理由，不再手工维护第二份字段副本。当前目录稿不预造空 Schema 文件。

### 5.2 数据、状态与提交

重要记录写清所属模块、标识、关系、生命周期、可变性及读取方式。选定存储后说明表／文档结构、唯一约束和必要索引；未选型时先说明逻辑结构和待决定问题。

对有副作用的操作说明先校验什么、读写什么、事务何时提交、哪些事件随结果保存，以及失败后已经生效的部分。跨模块操作明确各方写入责任；跨进程操作说明消息与业务结果的对应关系。并发和幂等只在相关位置展开，不给所有查询套用完整事务模板。

### 5.3 算法、时间与资源

算法给出输入域、步骤或公式、参数来源、跳过条件、边界处理和可复算样例。概率、时长及金额等数值说明内部精度与展示舍入；不能只写“使用 BKT”“调用大模型处理”。

涉及等待、超时或后台执行时，区分业务时间、运行时间与记录时间，说明时区和未知值。资源限制写明单位和测量办法；未取得数据的容量、延迟或费用写为假设并列验证方法。

### 5.4 AI 工作的具体合同

每类 AI 工作在所属模块中给出：触发条件、输入材料及允许来源、上下文限制、提示协议的位置、工具及权限、输出结构、程序校验、业务提交、继续或停止条件，以及语义质量检查方法。

LLM 生成候选与程序接受候选分开描述。身份、工具权限、状态转移和确定性计算由什么程序执行必须明确。模型超时、格式失败、语义无法确认和合法但无结果分别处理；不能都归为“重试”。底座共用机制只定义一次，业务文档引用。

## 6. 图与示例的质量

每张图写明标题和范围。节点名称与正文一致，箭头说明调用、数据流或依赖的含义；跨进程通信在选定后注明协议。不同图形、颜色或线型表达不同含义时给出图例，不依赖颜色传递唯一信息。C4 风格只用于合适的架构视图，流程、状态和数据关系采用相应图式。

本项目优先维护可审阅的 Mermaid 图源。新增或修改的图必须实际渲染并查看布局、连线、中文、裁切和阅读尺寸；语法通过不能代替视觉检查。过大的图拆成总体与局部，不靠缩小字体容纳所有信息。

JSON、公式、伪代码和图中的名称必须互相对应。示例数据标明用途；正常例子之外，对影响结果的关键边界给反例。代码块应注明是接口声明、伪代码还是实际实现，不能把示意代码当成可运行资产。

## 7. 决策、引用与文档维护

### 7.1 文档头与状态

工程文档头使用精简字段：版本、状态、维护与评审、写作规范、更新日期、修订说明。规范文件本身以§1列依据，不自引。输入基线、产品版本和完整变更清单集中在工程 README 与决定登记中，不在每份文档头重复长清单。

目录稿说明章节要交付什么；设计草案写出实际建议；已评审部分记录用户确认的范围。未决项放到相应章节或短表，标明问题、候选、影响和关闭条件。一个状态标签不能替整篇文档中的候选选择作决定。

### 7.2 修改与历史

每个发生修改的现行文档每批升版；新文件从 v0.1 起，规范首版为 v1.0。原文归档和实测资产按原字节保留，不为追赶版本重写。归档可读副本如调整链接或标注，须单独升版并保留精确原文快照。

当前引用指向现行权威定义，历史记录指向相应归档。新设计不拷贝归档正文。调整接口或状态时检查调用方、图、示例、数据约束和相关测试设计；变更记录说明改变了什么，不重演整个讨论过程。

技术命名、接口组织和数据边界等影响后续实现的细节，按用户要求提出具体方案并讨论确认。日常排版、引用修复与已授权整理可直接完成；批准文档结构不代表批准技术选型。

## 8. 评审与完成尺度

对拟进入实现的模块，作者先检查以下内容，再交用户审阅：

- 能从一个入口跟到成功结果，并指出每一步的处理者、输入、读取、写入和输出。
- 接口、字段、状态、图和示例一致；关键异常有明确返回及恢复方式。
- 实现者无需另行决定权限归属、提交边界、重复处理、关键算法或失败语义。
- 可根据设计列出正常、边界、并发和故障测试；语义质量与学习效果有相应验证入口。
- 未决事项及其影响可查；没有用旧候选、mock 或“以后补充”掩盖当前实现所需决定。
- 删除不增加设计信息的重复概念、空泛评价、历史复述及冗长表格。

检查深度按文档状态判断：目录稿只检查覆盖和分工，不要求已有接口或实验结果；详细设计按本节判断是否足够实现。检查记录写实际执行项目和剩余问题，链接已有结果，不新增填满勾选框的过程文档。设计评审与实际实现、测试通过分别记录。
