本文负责把当前产品阶段安排成可执行的工作，产品范围的唯一依据为 [Definition §5](../phase-3-definition/MVP_Definition.md#mvp-stages)，指标和判定规则由 [Validation](../phase-3-definition/MVP_Validation_Plan.md)维护。M1/M2/M3 是产品阶段，不是只在 Phase 5 切三批代码；每阶段先定义必要范围，再设计、实现和验证。

## 1. 总体交付目标与现状

当前目标是 M1：管理员从指定真实教材完成导入与建模，学生能够选用、讲解、提问和测验，系统依据实际评价主动安排后续学习，管理员能够维护内容并追溯运行。当前原型大部分采用 mock，旧 Spike/Build 只提供原范围证据；没有 M1 完成或试用准入结论。

现有三端原型、截图和全量规格继续作为设计资产。本轮停止优化后置页面，不要求完整家长端、错题管理、统计首页等先设计齐。M2/M3 的工作表在取得前阶段实际结果后才细化，避免再次一次性设计整个 MVP。

## 2. 产品阶段与实施顺序

| 产品阶段 | 当前投入 | 进入下一轮的方式 |
| --- | --- | --- |
| M1 核心闭环 | 完成 §3 的准备、工程和验证 | 汇总真实成功、失败、人工投入与质量限制，决定 M2 的需求优先级 |
| M2 日常学习与多角色完善 | 只保留 Definition 中方向与既有设计资产 | 先做 M2 的范围决定及必要设计，再实现和验证；不照单搬入全部旧页面 |
| M3 持续学习与效果验证 | 保留保持／迁移、主动策略改进与效果观察责任 | 基于前两轮真实数据制定有限验证和改进计划，再决定是否扩大验证或准备生产 |

M1 可以有内部实现工作项，但每项必须服务同一条完整主链。不得做完学生聊天便宣布第一阶段完成，也不得先建设未被当前链路使用的通用平台。

## 3. M1 工作项、依赖和产物

| 工作项 | 输入与前提 | 必须产出及验证方式 | 依赖与结束条件 |
| --- | --- | --- | --- |
| W1 范围与教材输入核定 | 本次分期决定、实际教材来源及已确认模型规则 | 按已确认整册范围采用电子源及全册目录，核对原件完整性、必做REQ子集及必要处理条件；版权页按DEC-041后补，不阻塞独立工作 | 来源选择及目录已完成；完整原件和实际处理条件分项跟踪。W2依据已采用源继续，不等待版权页 |
| W2 必要产品与领域交接 | W1 的范围；现有教材、教学、评价及主动介入规格 | 一条实际教材到教学／评价／任务的流程规格；实际扫描输入与人工核对参考；当前模型包及案例；处理 OPEN-010／012／013 的本链依赖 | 当前流程的输入输出、权限、状态、采用版本和未决出口可说清，M1/G3、G4 按范围评审；不要求全量 UI 重做 |
| W3 工程设计与最小运行底座 | W2 可接收合同及历史实现评估 | 明确接口和存储、真实模型／识别服务、结构化输出及校验、身份与空间、串行处理、配置和启动恢复；形成适量关键机制检查 | 技术方案能承载 W4/W5；无虚构模型能力或关键业务默认值，基础数据跨重启保留 |
| W4 管理员真实导入与建模 | W3 底座、实际扫描件与 W2 参考 | 在后台批量导入、整理原页及图表、核对修正、建立 Domain／Claim／课程目标及题库、应用；实际结果对照参考 | 整册各章完成建模并可选用，来源和适用方法可查；管理员不用开发者手改数据库 |
| W5 学生教学、评价及主动任务 | W4 的可用内容，W3 模型服务及状态合同 | 持续对话内讲解、提问、主动／阶段／结束测验；真实帮助与作答、Evidence／Belief、目标结果；学习后和到期任务安排、接受执行及暂缓 | 形成完整真实正常路径和必要失败分支；管理端可追溯并修正后继续使用 |
| W6 联合验证与 M1 交付 | W4/W5 的实际软件、内容、配置与用例版本 | 按固定计划检查主链、失败恢复、权限及语义质量，修复实现缺陷，交付运行脚本、清单、报告与限制 | 按 Definition §5.3 给出工程完成及内部质量结论；真实儿童试用另按相应 G6，不冒充已完成效果观察 |

W4/W5 可在已核对的小样本上逐步联调，但最终证据必须来自同一真实内容及运行链。不能一边用管理员真实数据、另一边用学生预写数据而声称整链已完成。可复用旧实现的模块需核查实际模型合同，不能把旧实验的通过标记直接继承。

**整册交付的实施方式。** W2 先用代表性章节验证导入、模型表达及教学接收合同；W4/W5 打通真实流程后，用同一工具和核对办法逐章完成其余内容，并边建模边联调。W6 对全册覆盖清单作逐章检查，对实际教学、检测与主动任务按预先确定的案例验证。样章成功是内部里程碑；不能因此关闭 M1，也不要求学生逐章学完才验收管理员整册建模能力。

**2026-11-02 工作进展。** W1 的教材选择已由DEC-041确定，13项目录及附页已有清单；版权页后补。W2 已交付[增加关系参考](../phase-4-product-and-domain-foundation/MVP_Domain_and_Content_Foundation.md#65-m1-当前模型的教材参考切片)：实际53–54页、当前对象关系、六题与13个评价对照，并完成静态检查。它不是整个W2完成，也不是正式应用内容。

接下来只补工程开工所需的三类交接：

1. 同步已确认的上位Task–Solution–KC关系（OPEN-012），避免工程同时面对两套关系。
2. 在现有样例上明确教学定义采用、选择冲突及未决处理（OPEN-013），并接上目标判断与主动任务所需输入；需要用户决定的产品变化单独提出。
3. 补基础解释和表图／跨页的少量代表输入、正式评价条件及校准安排，核对W2必要交接后进入W3。整册逐页建模由W4工具承担，不在工程前无限扩充手工样例。

## 4. 投入、负责人及运行安排

Codex 主导范围核对、设计、实现和验证；用户负责实际教材输入／使用条件、重要范围决定，并以管理员身份参与内容核对。同一人可以维护和确认，不引入双人审核流程。用户每日时间与费用不设虚构上限；孩子全部使用仍每天最多 30 分钟。

W3 在服务和材料确定后估算实际调用量、费用、等待时间和人工工作量。每次真实评测前固定本批案例、参考、配置、调用／时间停止点及重试边界；本规划不凭 mock 估一个工程完工日期。单个缺口若不影响独立工作项，继续推进；影响范围、权限或产品结果的决定提出讨论。

## 5. 检查、测量与问题处理

遵循 Validation §1.1 和 §4：确定性机制与语义质量分开，纯网络失败可按预定规则重试并单列，不带入语义结论。格式和实现问题及时修复、定向复验；不把可修工程缺陷遗留给用户复测。参考有误先修参考，模型不足则如实测量与限制，涉及模型无法表达的关键问题才提出设计调整。

不为“证明更可靠”无限加轮次。一次固定批次形成全部结果，必要修复只重验受影响范围；新版本与原结果分别记录，不把多版本成功拼成一个通过率。没有真实成功路径、权限越界或依据丢失属于当前阻塞；后置页面缺失、长期效果尚未取得不属于 M1 工程失败。

## 6. 阶段评审与变更

各评审在 [Gate 记录](../MVP_Gate_Reviews.md)注明 M 阶段、G3–G7、所审范围、版本和证据。用户本次授权修改规划，不等于 M1 已通过 G4/G5。涉及当前范围或既定质量目标的变更，先说明影响并取得必要决定，不能通过换阶段标签悄悄删去教材建模、评价或主动任务。

历史 G3 与旧 Spike/Build 记录原样保留。当前改用新内容／接口不要求迁移所有旧实验数据；生产使用的当前定义必须符合新合同，旧对象不得作为失效时的隐式替代。

## 7. M1 接收与后续阶段启动

M1 的完成条件统一引用 Definition §5.3，不复制另一套通过门槛。交付材料包括源码及构建、实际内容／模型／教学定义、运行配置模板与密钥设置说明、启动停止／恢复脚本、验证结果及已知限制。工程完成、内部质量通过与获准真实使用分别给出结论。

完成本阶段的真实实现与验证总结后，依据实际问题决定 M2 的范围并开始必要设计；不预先细化全部 M2/M3 页面。若 M1 未满足当前内部质量或使用条件，明确限制和处理责任，可以准备无依赖的后续事项，但不能以推进下一阶段掩盖当前阻塞，也不能放行相应真实儿童试用。
