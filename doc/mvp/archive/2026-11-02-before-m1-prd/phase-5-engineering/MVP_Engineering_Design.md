## 1. 实现范围与架构映射

映射产品能力、既有系统职责和工程组件；说明复用、补齐与暂缓范围，列出核心约束及影响实现的未决事项。

明确引用的 G3/G4 基线及其后续有效变更，列出对产品与领域交付的依赖；没有批准的输入不能只靠“最新文件”默认构成实现依据。

逐项说明旧原型、Spike/Build 代码可复用的实现、所依赖旧模型和需适配部分。旧实验保持原基线意义；名称替换或 UI 演示不能证明新模型路径已经实现。

### 1.1 M1 必须真实接通的责任

| 责任 | 当前必须交付 | 可简化与边界 |
| --- | --- | --- |
| Domain 与教材准备 | 批量扫描输入、原页及多模态内容保存、识别与核对、Task／Solution／KC、章节映射、题目及参考 | 人工辅助整理建模可用；不得预写 mock 替代整个导入链，不先追求全自动识别 |
| Learning Space | 教材与目标采用、活动范围、当前和历史版本、个人记录归属 | 一个实际课程即可起步；多学生／空间隔离不能省略 |
| Interaction | 采用教学蓝图／策略／规则，结合 Evaluation 选择动作；管理实际活动与展示；主动任务判断、安排及执行 | 少量策略及触发点，单活动串行；不做通用可视化流程引擎或日历产品 |
| Evaluation | 实际 Observation 对应 Evidence、单模板 Claim 内多维 Belief、条件有效性、目标派生 | 当前可取证方面真实更新，其余未知；不依赖写死掌握值或把点击完成当证据 |
| Reasoning 与工具 | 模型适配、上下文、结构化输入输出、语义检查、固定必要工具及失败分支 | 少量实际服务配置，保护凭据；语义规则加 LLM，程序不靠关键词猜教学含义 |
| Evolution 的最小维护职责 | 问题追溯、管理员直接改定义、保存版本、应用及后续使用验证 | 不建审批发布中心、自主改模或实验平台；定义修改不直接覆写个人状态 |
| 运行底座 | 身份、持久化、事件及引用、权限、日志、用量／延迟、故障定位、备份恢复和启动脚本 | 优先简单部署；不为未纳入功能建设通用基础设施 |

真实外部服务只替代需要模型判断或识别的步骤；权限、事务、重复提交和版本采用不能交给 LLM 保证。教材图／表与学生当前输入应按实际需要进入上下文，不能以纯文本检索丢失解题条件。状态和教学彼此依赖的合同、模型失败如何收束在正式编码前细化；无法解释的产品行为不能留给 prompt 隐式决定。

## 2. 组件、接口与运行流程

定义客户端、服务、任务和外部依赖的职责与边界，明确接口输入输出、错误语义、执行顺序和关键端到端流程。

接口合同给出请求与结果结构、前提、权限、版本、失败与重试含义及实际样例；与客户端呈现的状态和后台可查询数据一致。字段级设计可按增量完成，但不得把无法确定的业务结果留作代码默认值。

## 3. 数据、状态与一致性

设计数据结构、历史、版本、依赖、事务与状态转移，说明并发、中断、重试、重复处理和恢复下的不变量及检查方式。

Task Claim 模型变更的实现接收条件：只接受 TaskProficiencyClaim / Belief 的当前状态写入；对 TaskScope、责任、方法与实际支持做版本化校验；Domain KC 定义、关系与讲解用途继续可用。历史读取与当前解析分开，禁止旧 KC 缓存 fallback。迁移内容包、参考、目标投影与状态读写须有端到端证据，不能凭文档升版或旧 verify.py 通过宣称完成。具体接口和存储仍由本阶段设计。

工程接入须验证一个 Claim 的唯一模板绑定及内部方面定义，Evidence 的 ClaimVersion／AspectKey，和一个 Belief 内每方面的判断、不确定性、状态、依据及时间。提交仍由 Evaluation 单写一个修订，未更新方面保留原依据；查询检查实际要求的方面而非只看根 head。定义缺口、未知、失效、不适用分开，跨任务不能复制状态。旧 C1–C4 合入或多模板命题拆分须有来源与兼容证据，不能拼接分数或重复计权。

管理员对象维护按 DEC-026 实现所属页面直接保存，不再引入独立审批发布服务或要求每次变更建立 Evolution 事项。Domain、Learning、Evaluation 的责任层仍校验写权限、对象身份、引用与版本，并留存历史；语义规则导入不绕过定义检查。原型的浏览器存储和固定示例只作交互参考，工程必须接入真实持久化和后续学习读取。教材／目标普通保存不改变学生当前引用；按 DEC-032 在管理员明确应用后更新使用同一课程的当前引用，旧活动保留原版本。按 DEC-031 取消长期章节范围编辑，按 DEC-034 不补算原待映射作答；不得扩展为任意历史重算。

## 4. AI 与外部能力实现

按适用性定义模型任务、上下文、输出合同、校验、工具权限、失败处理与替代路径；区分系统确定性责任和模型判断，明确可追溯性、评测及质量限制。

产品层允许与禁止行为、用户控制、不确定表达和人工处置引用需求规格；技术设计只落实这些承诺。发现能力限制迫使改变产品行为时，登记影响并回到相应决定，不由模型策略自行补定。

模型任务引用 Phase 4 的具体领域判据与版本，区分当题反馈、Evidence 解释、Belief 推断和产品目标判断；说明输入、结构化输出、校验、未决及运行失败如何交给后续责任。实现正式领域导入及评测执行工具，检查交换结构、引用相容性和接入前后语义；内容错误回到对应资产维护，不在提示词中建立另一套未经批准的标准。

教学模型接收 [Product §3.9](../phase-4-product-and-domain-foundation/MVP_Product_and_Interaction_Design.md#teaching-model) 的蓝图、策略和规则，映射到 Interaction Policy 规范与 Interaction State 运行状态，不新增独立能力判断器。需具体设计定义保存与验证、运行版本绑定、当前阶段与检测状态、策略选择及调整输入输出、实际动作与帮助留痕、取消和恢复。语义判断依规则及 LLM，结构／权限／状态约束由程序落实；不能直接把 mock 分支或前端表单当作正式规则执行器。

按 OPEN-013 在真实接入前完成定义冲突、无适用策略、定义修改与已有活动的采用方案。若方案改变已确认的学生行为或权限，回到产品决定；不由工程默认值暗中补定。正式策略执行与 Evaluation 的成功／未决路径须分别验收，运行完成不自动写掌握结论。具体技术栈、Schema 和 prompt 仍待本阶段设计，本文仍是交付大纲。

M1 主动任务实现须明确触发事件、时间／到期检查、规则与模型输入、适用性检查、任务状态、去重及与实际活动的关联。至少支持学习结果触发和时间条件触发；允许在进入空间等时机检查到期，不要求外部推送。完成任务不直接等于目标达标，结果仍交给 Evaluation。题目先使用已核对题库，若本轮选择接入自动生成，须同时承担检查、保存、来源及使用验证，不把未验收生成路径用于正式检测。

AI 必要配置在 M1 完成，承载可先为受保护配置文件／环境与管理员检查工具；配置页面继续暂缓。服务标识、模型、凭据引用、超时／重试边界和调用记录必须明确，但具体供应商、参数值、存储和执行技术不在本轮规划预定。

## 5. 身份、权限与数据保护

落实角色与数据授权、敏感配置、外部处理、审计及数据生命周期设计；不以技术默认行为替代产品对可见性和数据操作的约定。

## 6. 性能、可观测性与运行维护

确定可观测事件、质量与费用记录、故障定位、兼容性、迁移、部署和恢复方案；指标引用验证方案，说明容量与成本假设。

将实际资源、调用成本与维护工作量对照 Phase 3 量级假设；关键差异影响可行性时进入共同风险或变更流程，不仅作为性能调参处理。

将 Requirements 的非功能承诺逐项落实为机制及检查；区分管理后台业务能力与部署、备份、首次管理员初始化等运行工具。交付清单关联源码与构建、配置、模型与规则、数据结构及迁移、领域与案例版本，使故障恢复和结果复测能够定位准确组合。

## 7. 技术取舍与验证责任

记录选型、替代方案、依据、风险和验证办法；将核心约束与失败恢复映射到工程检查，明确需要重开产品或系统设计的问题。

必备产出：核心运行与状态流程、关键接口合同及技术取舍说明。关系进入统一需求追溯主索引；跨阶段待决与风险引用共同登记册，确定性检查和模型测量的责任遵循验证方案，不在本文保存另一套通过门槛。
