## 3. 每类输出只维护一份

| 输出 | 位置与职责 | 创建／完善时机 |
| --- | --- | --- |
| 产品规格主文档 | `m1/PRD.md`：目标、范围、用户场景、全流程、功能规则、模型与数据含义、权限、AI责任及验收 | 按业务包与详细规格、原型同步迭代，保留完整产品图景 |
| 产品详细规格与原型 | `m1/design/`：分步操作、状态、截图、教材与模型对应、题目及评价标准；原型代码在`m1/prototype/`，旧代码按需复用 | 有范围草稿即交叉展开；具体操作和内容可以返回修改PRD，按包共同评审 |
| 工程设计与交付 | `m1/engineering/`：总体设计及业务、Space、基础底座、客户端和部署设计；各模块维护自己的接口、数据及实现机制 | 总体设计已有正文，按主流程交叉细化模块合同；技术细节须审阅，不由工程补定核心需求 |
| 验证计划与报告 | `m1/validation/`：测量方法、样本、配置、停止条件；实际结果另成报告 | 计划在运行前形成；有真实执行后才建立结果报告 |
| 决定与待决 | `DECISIONS.md`：承接、变更、未决、阶段评审及版本记录 | 随需求推进维护；不另复制PRD正文 |

文件不必一开始全部创建。design已承接领域、教材、评估、目标与Interaction的产品规则，原型及截图表达已确认交互，真实评价链尚未完成。engineering按SwDD进入模块详细设计，本批展开Domain并同步直接相关合同；原型未修改。validation已有有限真实提取试验，结果按原报告保留，不据本稿改判。PRD、详细规格和原型共同表达产品设计，工程设计定义实现机制；现行Task／Solution模型及旧资产边界见决定登记§68—69。

## 4. 历史与资产的使用规则

- 原MVP文档和截图整体进入[归档入口](archive/README.md)，不继续在旧正文中填新需求。已经确认的决定不会因归档自动失效，承接过程见DECISIONS。
- 当前M1原型在[独立目录](m1/prototype/README.md)，默认端口5182；[旧原型](../../src/mvp_prototype/README.md)保留为参考，默认端口5181。当前包含领域手动管理、教材助手持续对话、候选核对及采用、待入库处理、章节关联、Claim、目标管理、四类活动管理及学习空间追溯；学生默认打开独立活动森林示例，原有记录入口单独保留，均为mock，真实执行和评价按工作包推进。内容参考仍在[准备资产目录](../../src/mvp_foundation/README.md)，不把样例当作实际建模结果。
- 只有与当前M1需求有关且核对过的旧内容才迁入新PRD；不整篇复制旧文档后换名称。需要改变已确认决定时说明理由并讨论。
- 每次修改文档均升版并记录；旧冻结输入和真实运行结果不重算、不改判。当前图文设计发生修改时，文字、原型及截图仍需同步。
