## 1. 阶段对应与工作顺序

目录编号对应 [Development Roadmap](../top/DeerMind_Development_Roadmap_v0.3.md) 的项目阶段，不对应 System Design Roadmap 内部阶段。原阶段顺序、目标和 Gate 含义保持。

| 阶段与目录 | 要回答的问题 | 阶段交接 |
| --- | --- | --- |
| `phase-3-definition/` · Phase 3 MVP Definition | 为谁解决什么问题，完整 MVP 包含什么，为什么值得做，如何判断结果？ | G3：定义足以支撑产品与领域基础工作 |
| `phase-4-product-and-domain-foundation/` · Phase 4 Product & Domain Foundation | 用户如何完成目标，运行需要哪些领域与内容、数据权限及评测材料？ | G4：交互和实际基础资产足以支撑工程实施 |
| `phase-5-engineering/` · Phase 5 MVP Engineering | 如何分步实现、验证、运行并交付完整 MVP？ | G5：核心价值链真实可用，可进入 Internal Alpha |

Phase 6 Internal Alpha & Evaluation 和 Phase 7 Controlled Pilot 是后续独立阶段。前三阶段要准备其验证设计和输入，但不提前声称取得其质量或真实使用结论。Phase 5 内部可以分多个增量实施；增量不是新的 Roadmap 阶段，也不等于把完整 MVP 定义缩成一个活动。

当前工作是整理并重新评审交付框架，随后复核产品定义。历史 G3 记录保留，但不能跳过对新范围及其依赖的确认而直接沿用旧基线实现。已关闭的架构 Spike、Build 及系统设计基线不因本次整理重开。

## 3. 大纲的通用性与信息归属

大纲采用可复用的问题结构，不预设某个学习活动、客户端、技术栈、模型供应商、题量、样本数或成功阈值。它仍须覆盖领域内容、AI 输出、数据和权限等适用责任；通用不等于删去项目类型必需的栏目。具体项目填充时说明适用性，确实不适用的栏目可以给出理由，而不是为了填满模板虚构需求。

产品定义负责“为什么、做什么、边界”；需求规格负责可观察行为；验证方案统一负责指标和结果判定；产品与领域基础负责交互、数据权限和实际运行材料；工程文件负责实现与实际交付。后续文档引用前序决定并补充本层内容，不复制整套范围、指标或验收表，避免出现多个互相冲突的版本。

需求决策表放在产品定义中，是核心组成部分，但不能代替角色情境、问题依据、价值假设与范围推导。活动应从确认的需求导出；旧四活动划分、后续候选划分和现有原型均可供比较，不预设任何一种已经正确。

## 4. 评审顺序与内容填充规则

首先评审阶段对应、交付物是否必要且充分、责任是否重叠、各大纲是否能够支撑下一阶段。**框架与大纲确认之前，不开始新文档的项目内容填充或据此修改原型。**

确认后，先梳理已有需求来源与明确决定，区分观察、推断、假设和仍待讨论的取舍，再形成需求比较与整体范围。随后把需求转为活动和流程，准备领域、数据权限与评测基础，最后按 G4 输入开展分步工程实施。不能由现有页面或实现方案反向决定需求。

不确定事项必须记录影响、需要的依据、负责阶段和决策节点。影响当前产品方向或跨层合同的未决事项提出讨论；属于后续阶段的细节可以明确留待该阶段，但不能假装已解决。文档大纲完成、内容完成、资产完成和阶段 Gate 通过分别判断。
