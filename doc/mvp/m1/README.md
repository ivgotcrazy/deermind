M1的产品设计由[PRD](PRD.md)、[详细设计](design/README.md)和[交互原型](prototype/README.md)共同表达。当前按业务流程分包推进：每包同时整理规则、实际内容与操作，互相核对并允许返回修正，不等待整份文档写完才开始另一份。以下是产品设计计划，不是开发排期，也不表示任何包已获工程接收。

## 1. 目标与共同输出

管理员能够导入指定北师大六上数学教材，核对图文、完成建模和课程准备，再应用给学生使用。学生可以选用、讲解、提问和测验，得到有依据的反馈评价；系统可安排必要后续任务，管理员能追溯和修正。M1最终须通过实际工具完成整册建模，版权页可后补，不能以一章或全书上传代替。

每个工作包共同交付以下结果，写回已有位置，不另建六套PRD或六份专题报告：

| 输出 | 必须能回答什么 | 维护位置 |
| --- | --- | --- |
| 业务规格 | 谁在什么情境下，为何操作；前提、输入、过程、输出、状态、权限及必要例外是什么 | PRD对应需求及验收场景 |
| 详细交互 | 从哪里进入，每步看什么、做什么、得到什么；为什么这样呈现；正常、空白、处理中、失败及恢复等适用状态如何表达 | Interaction Design对应流程、原型及实际截图 |
| 内容与模型规格 | 读写哪些业务对象、引用哪些版本、题目和图文怎样对应；实际输入及合格／不合格／未决结果是什么 | Content and Model Reference对应小节；通用模型语义引用上位设计 |
| 可走查的原型资产 | 用同一组mock讲清步骤和反馈，截图与文字对应；不需要真实OCR、LLM或跨菜单数据库 | 复用V2基本布局和持续对话；源码及截图按工作包索引 |
| 接收记录 | 哪些需求已覆盖，证据在哪里，哪些问题待决定或留工程；交接的确切文档及资产版本是什么 | 本文工作表、PRD验收、DECISIONS中的决定与审阅；实际测量方法归validation |

同一规则只有一个完整维护位置，其他文档引用。PRD保留完整业务图景；详细规格和原型反映出需求缺口时，回到PRD修正。任何一份文件、mock或截图单独完成，都不表示该功能可以交接。

## 2. 六个产品设计工作包

按下表顺序集中处理，每包均横跨规则、内容和交互。账号、权限、版本、AI与人工分工、用时提醒和失败恢复随相关步骤一起设计，不拖到最后补写。

| 工作包 | 要交付的业务结果 | 主责需求／验收 | 共同设计必须覆盖的操作与内容 |
| --- | --- | --- | --- |
| M1-D01 教材导入与整理 | 一批扫描件成为按章组织的KC、题目及教材解法候选，并可提交领域处理 | R02–03／A02–03 | 必选领域、批量输入、内容与原页、重新解析并采用、分别选择提交、继续与删除；不建设复杂块编辑器 |
| M1-D02 建模与课程内容准备 | 形成可复用领域定义与实例、章节采用、评价目标、Interaction 活动定义和题库 | R04–07／A04–07 | 先有Domain手动管理；处理KC、题目、解法待入库，分清模板与实例；章节Task／Solution关联；再准备Task Claim、目标、讲解／答疑／检测定义和合格题目 |
| M1-D03 应用、选用与进入学习 | 管理员准备的内容可被合适的学生选用，学生知道当前能做什么 | R01、R08、R10、R17／A01、A08、A10、A16 | 首次启动、必要服务就绪与试用账号、必要告知；保存与应用、版本采用；学生选教材和目标建空间、按次选章和读原页；部分可用、空间隔离及更新后的引用 |
| M1-D04 讲解、答疑与活动控制 | 学生在持续对话中获得适当帮助，并能调整、暂停、恢复和结束学习 | R11–12、R16、R19／A11、A15、A18 | 讲解与答疑的不同主线、分段讲解、局部追问、必要回补、受助练习、活动树切换与继续；实际帮助、输入保留、只提醒不强制结束；无合法动作或服务失败的反馈 |
| M1-D05 检测、反馈与评价 | 一项检测活动通过多个原子检测轮获得条件明确的表现、个人判断和目标结果 | R13–14／A12–13 | 题目计划与负担、检测轮作答与帮助边界、轮后答疑／讲解、新题重新确认、活动结束反馈；同题重复、只答数值、理由错误、受助成功、有效未知；Evidence→Belief→目标的区别及延迟基准 |
| M1-D06 后续任务、运行追溯与修正 | 系统基于有效依据提出下一步，管理员能沿一次活动找回依据并修正 | R09、R15、R18／A09、A14、A17 | 主动任务接受／暂缓／拒绝及再提醒，返回已有教学或检测；实际展示和提交、模型判断、服务失败分别追溯；修正内容、应用新版和失效结果退出当前使用 |

表内使用PRD的M1-R、M1-A编号。R17的身份权限与数据含义由D03统筹、每包落实；R18的AI／程序／人工责任与运行边界由D06汇总、从D01就开始检查；R19的用时规则由D04落实，运行质量与验证方法贯穿全部包。需求归属不把这些责任限制在单一包内。

**依赖与允许返回。** D02的Domain手动管理先于教材入库；D01选领域后解析内容，再返回D02处理候选，最后在教材建立章节关联。D02其余部分使用这些范围准备Claim、目标、Interaction 活动定义和题库，D03再应用给学生。不是先写完D01才能建Domain，也不是没有全领域模型就不能导入教材。D04／D05使用同一课程实例，D06任务回到讲解、答疑或检测；任一包暴露语义缺口可返回上游修订。

## 4. 每包的推进与完成判断

1. **走业务。** 从一个明确场景出发，核对输入的来源、每个操作者、系统处理及结果去向，列出必要失败分支。
2. **对照三类表达。** 同时修改PRD规则草稿、详细规格与mock方案；内容和界面提出的问题可以返回业务定义，不维持单向文档顺序。
3. **形成可审阅资产。** 确认必要调整后复用或修改原型，用逻辑一致的mock展示实际操作。给步骤编号`M1-D01-S01`等，文字记录输入、处理、输出、状态与设计理由，并链接对应截图和原型位置；没有截图的步骤明确待补。
4. **自行走查后提交审阅。** 正常路径及必要分支逐项对照，发现实现问题及时修复；产品决定由用户确认。跨包问题回写相关位置，不静默加入新范围。
5. **记录接收范围。** 本表更新完成情况与证据，DECISIONS登记重要决定和审阅版本。可接收部分供工程分析，受未决问题影响的部分继续设计。

一包达到可接收状态，至少需要：

- [ ] 场景、前提、输入、操作、反馈、权限、状态和必要失败行为具体，前后生产者与使用者能对应。
- [ ] PRD、详细规格、原型和截图表达一致；每步能定位实际画面，相同画面可复用，但须明确对应哪个操作和状态。
- [ ] mock的教材、对象、题目、帮助、表现和评价结果逻辑相符；不要求真实AI或全菜单数据同步。
- [ ] 有合格、不合格和未决等适用例子，能解释依据；已有试用门槛不被改写成普遍测量定律。
- [ ] 需求与验收对应，无阻塞该范围的产品疑问；技术问题明确交给工程，实际质量交给验证。
- [ ] 用户需要决定的事项已处理，尚未审阅与作者自检如实区分；不把计划或局部完成当成Gate通过。

六包共同走查后，再核对整条主流程及整册准备要求。原G3／G4分别检查产品范围与设计资产责任，不表示两类工作必须串行；正式工程接收记录确切范围、版本和依赖。可以在设计期间进行必要技术可行性分析，不能由编码默认值决定尚未确认的产品含义。

## 5. 本轮交付边界

当前已同步领域、教材、评估、目标及四类活动配置。18张本批截图和13项相关浏览器检查支持有限 mock 的交互复核，不代表完整D02、真实能力评估、整册建模或M1 Gate通过。正文待用户审阅，后续工作以本表缺口为准。

产品设计不要求提前手工完成全册模型；先确定真实工具要支持的业务，再由实际工具逐章建模并验收。首页统计、完整家长端和广泛自动化优化不在当前主线。
