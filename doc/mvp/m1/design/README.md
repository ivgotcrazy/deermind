## 1. 共同输出及唯一维护位置

| 输出 | 完整维护的内容 | 引用关系与边界 |
| --- | --- | --- |
| [PRD](../PRD.md) | 目标、范围、场景、端到端业务、核心规则、对象的产品含义、权限、AI责任、验收 | 给出完整产品图景并指向详规；通用Space语义引用上位设计；重要业务改变回到此处确认 |
| [Interaction_Design.md](Interaction_Design.md) | 每步入口、可见内容、输入、操作、输出及状态，必要分支、设计理由、原型截图和定位 | 展开PRD需求；业务规则引用其唯一位置。页面变化、文字变化或内容变化时检查相互影响并同步修订 |
| [Content_and_Model_Reference.md](Content_and_Model_Reference.md) | 教材与业务对象的对应、内容准备条件、任务与方法、题目及参考、具体教学与评价标准、正反例和未知 | 承接PRD中的内容要求。已确认标准、设计草案、示例与待验证项分别标明；此文件不以“参考”名义降低规定的效力，也不把作者例子升级为正式内容 |
| 原型及`assets/` | 可操作的流程、mock状态、截图／图示与来源 | 可复用V2布局和对话。截图说明已展示什么，不能替代隐藏业务规则或证明模型效果 |

三份文字文件共同构成产品规格，原型用来呈现和检验。数据库、API、服务部署、LLM提示词实现和真实算法在engineering；内容质量与语义效果的实测方法及结果在validation。产品侧仍要定义可观察行为和可接受结果，不能把这些推给工程。

## 2. 用一个功能说明分工

| 同一功能：检测中求助 | 应写清什么 |
| --- | --- |
| PRD | 实质求助先结束整次检测，再讲解；已提交表现和实际帮助保留，未做题不判错 |
| 交互规格及原型 | 求助入口、结束告知、如何在同一对话讲解、哪里查看已提交题及本次结果；正常完成与提前结束如何不同 |
| 内容与模型规格 | 本例题面、解法、参考答案、受助与无当题帮助的判据；一次作答如何支持Claim不同方面，哪些结论不能推断 |
| 工程设计 | 请求、记录、串行、中断和模型调用如何实现，怎样保证规定的帮助与评价顺序 |

例如“求助结束整次检测”只在PRD维护完整业务规则，详规引用并展开表现；“增加四分之一”的两题及七天标准只在内容规格§4.10完整维护，PRD引用其适用范围。若详规与PRD矛盾，应定位并修正，不能让实现者任选一份。涉及通用模型责任的矛盾，还须同步其上位定义。

## 3. 同步推进与接收

先有场景和范围草稿，再同时展开规则、实际内容和交互；原型暴露的输入、反馈或状态缺口可以修改PRD，内容例子暴露的模型缺口可以修改详细规格及上位合同。这里的同步指交替核对和共同完成，不要求每次编辑都改动所有文件。

每包沿现有文档补充，不额外建立一份PRD。步骤应有编号、原型位置与对应截图；同一画面支撑多步时明确关联。数据使用mock，保持教学与评价逻辑一致；不要求接LLM或实现所有菜单之间的数据持久化。

共同完成条件、状态与评审记录位置统一见[M1工作计划](../README.md#4-每包的推进与完成判断)。原型方案已有授权的继续执行；新业务决定或尚未确认的界面调整先形成具体方案再请用户确认。后续正文、页面或mock变化时，同批检查截图，不将旧截图冒充新状态。
