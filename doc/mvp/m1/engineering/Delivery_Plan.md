## 1. 设计接收与依赖

用户已基本确认[总体主流程](System_Design.md#72-总体架构问题清单)，并授权模块详细设计。本批按§2.7完成主流程文档核对并修正交接遗漏；配置候选仍待审，未据此确认容量或授权编码。

总体确认状态与未决项统一见[总体§7.2](System_Design.md#72-总体架构问题清单)，后续工作见[收口检查](System_Design.md#722-总体收口检查)。本计划只维护交付顺序、验证责任与证据；E01–E07顺序保留，已有Operation细节仍待审，本轮未授权编码。

每项实现工作引用[AI Operation及普通入口目录](README.md#5-m1-operation总目录)中的名称和责任章节；普通API／消息不创建Agent包装。进入实现前核对：

- 调用者、权限、输入输出及正常分支已明确，传输Schema有唯一来源。
- 需要持久化的Step、事实事件、幂等身份、失败恢复和提交边界已定义。
- 跨Space输入与结果名称对应，等待释放资源，重试不重复业务效果。
- 已确定本工作项所需的存储、调度、模型与客户端适配；未决项明确阻塞哪一步。
- 至少有正常、非法输入、重复提交及关键中断恢复案例，期望结果来自合同。

当前AI Operation、普通处理及共用机制是待审草案，传输Schema、表约束和技术选型尚未全部落实，不因总目录齐全就宣布各模块可直接开工。用户审阅关键合同，Codex据此逐项实现和验证。

Domain实现前须落实三项交接：Product的来源读取／锁定端口；公共运行的同事务事件和接续登记；基础设施的连接、权限与迁移工具。Domain表及普通请求键由Domain维护，不在E01重新定义。设计中的来源竞争、版本冲突、同键重试和提交中断案例转为实现阶段集成测试，不在详细设计阶段先写验证代码。

E02沿Product§3—4.1；E03定义与目标接线沿Evaluation§1／4／6.4及Product§4—5。Evidence／Belief接线沿Evaluation§2.3—2.4、§3.3、§5.6及§6.6；新增来源去重、部分资格、事务失败和快照覆盖用例。评价按§6.7同空间顺序处理，保持按§6.8使用服务端时间；Interaction事实与活动执行已有详细稿；公共运行的事务交接与派发稿见§3—4；基础设施继续关闭实际配置及迁移。

正式实现沿[总体§5.1](System_Design.md#51-已确认的源码组织)组织：后端Python＋FastAPI，API和Worker共用模块；前端Vue 3＋TypeScript＋Vite，一个工程两个入口。E01承接启动与共用模块装配，客户端增量在同一前端工程中接线；不重新比较已定框架，不直接复制原型mock作为正式实现。

## 2. 必要技术验证

Temporal＋Pydantic AI＋NATS JetStream＋PostgreSQL及Kubernetes生产部署方向已定，不另设独立选型PoC。按已定方案推进模块详细设计，版本、资源和部署参数待确认；数据库工具及物理实例边界见基础设施§1—2，备份步骤见§6。

[总体V01–V08](System_Design.md#73-技术验证的范围与完成条件)保留为设计及实现检查入口；V03／V04／V07的重复投递、早到通知、进程中断和恢复检查纳入E01及后续接线测试，不作为开始设计的门槛。其他语义、数值、容量与浏览器验收沿既定范围进行，测试条件和实际证据在对应实现工作中记录。本批未执行运行测试。

V01采用[总体§1.3](System_Design.md#13-已确认的试用与容量验证假设)的输入：首批总人数上限100人，首轮验证10名学生同时学习，并有管理员同期导入教材。10人不转换为固定LLM并发数；请求节奏、测试时长、模型限额、资源配置和通过阈值在试验前提出并确认。资源不足场景按最新决定检查：明确返回错误及提示，已受理输入和已完成结果仍保留；不设置教学优先、资源预留或教材降速的验收要求。本轮未执行容量或资源不足测试。

V05／V06的权限验收区分两层：底座拒绝跨空间资料引用和未授权工具，所属Operation拒绝违反业务规则的动作。覆盖教材指令不能扩权、合法候选保存、独立检测求助的先后顺序，以及拒绝后的明确反馈与允许部分接续；不把权限通过当作语义正确，也不新增权限管理页面。还须核对外发内容由Operation组织、未配置模型服务不能调用，以及服务凭据不进入提示词、客户端或普通记录；不安排材料标记或内容审查机制。以上均为后续实现验收项，本轮未执行。

V07按[总体§6.4](System_Design.md#64-已确认的恢复目标)检查停机后的接续：覆盖业务PostgreSQL、Temporal执行数据、NATS消息交接数据和教材原件，以及恢复后的输入、结果、待执行任务和引用是否对应。各自采用何种备份或重建方式在基础设施设计中确认，不强制相同机制，也不以持续不中断为M1门槛。实际恢复时长、结果和损失范围须有证据，验收前批准指标，不预填通过。

文件存储按[总体§5.3](System_Design.md#53-文件存储与初期部署)接入。E01实现统一文件访问与文件系统适配；初期API、Worker在同一节点挂载同一个local-path PVC。V07检查API写入后Worker可读、进程重启后文件仍可读及原件备份恢复；不以此宣称节点故障可自动跨节点接续。共享存储或对象存储后续按需接入，初期不同时建设多套适配或迁移平台。

日志与事件在E01建立共同记录及关联方式，E02—E07按业务补齐。验收须从某学习空间查询并筛选事件，再定位所属普通处理或AI Operation、必要的模型／工具调用日志和结果；失败记录应让人看清失败位置与原因。日志完整性、可读性与事件查询单独检查，不以存在日志文件代替通过，也不把技术日志当作正式事件。具体字段、级别及查询条件先设计审阅，不新增监控后台。

聊天与事件分存的验收归V06／V08：消息历史显示原文，空间事件按范围查询，Evidence沿来源事件及引用取得授权原始内容；同一消息关联多个事实不产生重复聊天记录。V03／V07继续检查提交中断及备份恢复后正文、事件与关联均可追溯。字段和具体用例随后设计，本轮未执行。

模型API按[总体§6.1.1](System_Design.md#611-模型api接入边界)由AI底座统一接入，E01承接受控连接及按Agent配置；不建设模型推理平台。E02／E04／E05分别核对教材助手、学习助手与证据解释的输入输出能力；各类Agent共用模型时，仍分别检查上下文和工具权限。具体供应商、型号与配置合同先审阅；E02按[总体§6.1.2](System_Design.md#612-教材agent解析与对话修正)验证教材Agent解析、按提示修正、核对及采用，不安排独立OCR接入。先用既有代表样例检查补漏、公式、解法拆分和局部修改范围，再按既定计划完成整册验收；API接通不作为教材、教学或证据解释的语义验收通过。

责任文档在详细设计评审时提出测量条件、阈值建议和未达到时的处理，由用户确认；本计划汇总已批准依据和证据位置。影响总体边界、通信或部署方向的要求在总体接收前确认，其余在对应详细设计接收且相关验收执行前确认。不得测试后再定通过线；本轮不填写数值、不声称容量或恢复已验证。

主流程接线验证还须覆盖：统一进入`domain.supply_task`，库存足够不生成、不另设Interaction筛选；题单就绪只返回摘要，确认作为下一条消息才开首轮；Evaluation先查询事件再经内容所有者授权读原文。用[事件目录](README.md#6-跨模块事件目录)核对触发方与使用方，未命名事件及字段在详细设计中确认。

本批接收检查另含：占用入口后派发失败恢复、停止后的迟到候选、答案提交与反馈交接、重连不重做、无／迟到显示回执不影响概率，以及教学与作答事件的提交顺序。先按文档检查合同，实际数据库、LLM及浏览器验证在实现阶段执行。运行交接与AI调用已有详细稿；认证和WebSocket本批已形成详细稿；下一批细化基础设施启动、存储迁移、配置和恢复，E01—E07实现顺序不变。

本批E01／E04／E05接收另含：Ack后业务失败仍可查、启动回应丢失不建第二个Workflow、等待到期先补查、已超时接续不重启、旧尝试输出被拒绝、候选已存不重调模型、评价通知乱序仍按源顺序处理。证据归公共运行日志、事件及各所有者收据；只能在实现阶段故障注入后登记通过，不把本文设计走查算作运行验证。

AI底座接收增加以下检查：受理后改配置及密钥轮换；故障不自动换模；工具失败也计次；来源超限不静默删减；候选已存只补业务提交；取消后产物不生效。具体案例见[AI底座§7](AI_Foundation_Design.md#7-接收检查与未决项)，字段不在计划重复。当前均为待实现验证。

本批E01／E04补认证与通信接收案例：缺确认／越权输入被拒；登录退出与后台继续分离；重置后旧Cookie不能读写；多标签换账号不串数据；断线前已受理不重复保存；通知遗漏可补读；停止回执丢失不重启；重连不重复进入空间。详细输入及期望由Product§2、公共运行§5、Client§5维护，当前未运行测试。

本批E01／E02增加文件与维护接收：上传中断不形成ready，收据丢失可查原身份，文件先保存再提交引用；错误挂载拒绝写入；重复初始化不清库；迁移失败不启动新服务；同一备份恢复后核对正文、事件、Step与消息位置。验收案例见基础设施§7，实现时执行，不在设计阶段跑验证代码。

本批E01／E04／E05补预算接收案例：同一恢复命令不续时，授权新尝试可越过旧截止时间但不能清零用量；自动重试不续时；聊天转检测不加额；已保存候选不重调模型；旧Wait不因恢复重开；Ack后AI失败不重投事实事件。实现时执行，本轮只核对合同。

本批增加E01／E02接收案例：全册上传与单次模型限额分开；跨页材料超量保留覆盖和关联；无consumer不发布、暂停不删durable；投递耗尽通知缺失可由收据核对发现；授权重送不重复业务；Temporal历史过期仍按已存Step恢复，不把NotFound当作未执行。代码验证留实现阶段。

## 事件事实源修订的实现接收

依次落实：事件信封/正文及附件 → 事件管理与同事务投影 → 各模块写入口 → 原文查询与Evidence来源 → 订阅补读及维护重建。现有9项AI能力和主流程顺序不变；不先编写绕过事件的业务写入。

| 检查 | 接收证据 |
| --- | --- |
| 生产者事务 | 事件追加后投影失败整笔回滚；重试只返回原结果 |
| 原文闭包 | 不读取消息/作答业务表，仍能取得当时题面、提交与帮助原文 |
| 事件覆盖 | 正文登记每个P表都有产生事件，业务变化不能只改查询行；控制数据有重要变化留痕 |
| 消费幂等 | 收据、投影和已检查位置一起提交；重复通知无重复效果 |
| 历史/实时交界 | 固定上界前无遗漏，之后连续接续；新增范围也可发现 |
| 受控重建 | 保留原ID、版本、概率及来源；不调用AI、数值更新，不发旧通知或启动任务 |
| 权限 | 可看事件列表不能绕过原文/私有记忆/模型材料授权 |
| 整批恢复 | 事件及附件hash一致；执行恢复与业务投影重建分别核对 |

以上均是实现阶段接收条件，本轮未运行产品、数据库或消息系统。EventPartRef和正文DTO改变旧载荷；代码生成需从本轮合同起步，保留旧文档解码兼容说明，但不编造尚未上线的数据迁移结果。
