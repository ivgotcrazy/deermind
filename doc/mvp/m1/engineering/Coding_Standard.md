## 2. 通用写法

- UTF-8、LF、文件末尾换行；不用Tab缩进。Python为4空格，其余代码及配置为2空格。格式化目标100字符，长引用、模板和生成内容不强行截断。
- 标识符用英文，领域术语与合同一致；业务说明、注释可用中文。Python模块/函数/变量用`snake_case`，类用`PascalCase`；TS变量/函数用`camelCase`，类型与Vue组件用`PascalCase`；真正的常量用`UPPER_SNAKE_CASE`。
- API、事件和数据库字段沿用已定合同，不为了风格统一擅自改名或增加一层转换。Helm values沿上游字段命名。
- 函数解决一个明确问题；不按行数机械拆函数。确有复用再提取公共代码，不为所有功能建立接口、工厂、基类或配置项。
- 注释说明原因、边界和约束，不逐行复述代码。公开接口或有副作用/重要异常的函数补简短说明；简单私有函数无需模板化长注释。
- 不保留大段注释掉的代码；暂留事项注明具体问题和处理条件。禁止不说明理由的整文件检查关闭或类型绕过。

### 2.1 可读性是交付要求

- 一个语义动作一行，不把多个变量初始化、分支、执行和退出挤成一行。简单且清楚的单条guard可保留；多条件加失败处理使用展开的`if`。
- 按“准备输入、执行动作、校验结果／收尾”等逻辑块留空行，不在每条语句后机械加空行。长参数列表一项一行；复杂表达式先命名中间结果。
- Python顶层函数／类之间两空行，方法之间一空行；Shell函数之间一空行。格式器能排版，不能替作者识别段落边界。
- 名称说明对象或目的，例如`password_key`、`helm_calls`；不使用`r`、`db`等让读者反复回查的缩写，明确的局部数学变量除外。
- 文件头说明用途、入口、依赖及重要副作用；复杂函数说明调用约定。注释解释原因和约束，例如为什么不启用hooks、为什么使用临时配置、清理顺序为何重要。
- 测试夹具中的可执行代码也须可读、可检查；较长的Python／Shell替身放独立夹具文件，不能用大字符串避开lint。故意错误的最小检查器样例需标明用途。
- 不以增加注释掩盖结构问题，也不为了减少行数压缩代码。只在有独立职责或复用价值时提取函数，不创建一次性通用框架。

## 3. 后端、数据和AI代码

### 3.1 Python与模块

函数参数和返回值写类型；测试方法与脚本入口也包含在内。正式业务源码采用严格类型检查；当前部署测试和检查工具采用Pyright standard加Ruff函数标注检查。外部JSON在读取边界验证或明确限定类型，不能到处传递无结构字典。

`Any`只可用于确实动态的第三方协议/测试材料边界，须就地说明；正式业务合同不得用`Any`替代Schema。类型断言不等于运行校验。客户端、模型和工具返回均视为不可信输入。

按源码组织的公开合同调用其他模块。底座不能反向导入业务，不能跨Space导入私有存储。公开合同导入时不创建数据库连接、模型客户端或后台工作。纯概率函数不依赖FastAPI、Temporal、数据库或模型SDK。

当前自动规则检查直接Python导入和客户端shared反向导入；正反样例验证规则有效。动态导入、SQL越权、间接I/O和导入副作用仍需评审及集成测试，不能把静态检查当完整授权证明。正式模块建立时，按已定依赖矩阵补齐实际路径并纳入严格检查。

模块、公开类／函数和测试入口有docstring，先用一句话说明职责；非显然的参数、返回值、抛错及副作用再补说明。测试方法说明其保证的行为，不复述函数名。复杂接口可采用`Args`／`Returns`／`Raises`段落，简单函数一段即可；类型由标注维护，不重复抄入注释。

导入放模块顶部并按标准库／第三方／本项目分组，禁止通配符导入和导入时执行外部操作。资源使用上下文管理或明确的`try/finally`释放。时间使用已定服务端口径，不能混用带时区与无时区值。

### 3.2 错误、异步和事务

- 区分业务拒绝、外部故障和程序错误；只捕获能处理的异常。边界确需兜底时保留异常原因并转换为统一错误，禁止空`except`、返回空值冒充成功。
- 外部访问有时限；异步函数不执行阻塞I/O。停止与取消按所属工作的合同传递，不误取消已经受理的评价。
- 重试沿已定层次和总预算执行，不在函数内部自行叠加重试。幂等由稳定身份和存储约束实现。
- SQL参数化；表结构只经迁移脚本变更。跨模块共同事务由既定端口协作，各模块只写自己的表。
- 模型调用、远程请求及长计算在数据库短事务外；失败回滚，不遗留半批有效业务数据。

### 3.3 日志与AI能力

应用日志遵循[公共运行§6.1](System_Foundation_Design.md#61-必记日志与存储)的字段表及正常／异常示例：UTF-8、单行JSON，输出到stdout／stderr；不另设字段别名。异常在负责处理的边界记录，避免各层重复整段堆栈。禁止打印凭据、Cookie或完整学生正文；详细业务材料通过授权事件查询。日志不代替只追加的事实事件。统一日志封装尚未实现，在对应工程增量接入；本轮仅补文档。

提示词、候选Schema、验证器和固定样例归所属Operation；不将提示词散落在API或通用底座。模型只能提交候选，程序执行权限、规则、事务、概率更新和正式保存。Workflow遵守可重放限制，非确定性I/O通过已定执行步骤完成。重放测试、真实模型质量与费用检查在相应增量实施。

## 4. Vue与TypeScript

- Composition API与`<script setup lang="ts">`；props/emits有明确类型。TypeScript开启strict及索引空值检查，外部未知值先校验，禁止用`any`绕过检查。
- 页面组合组件，组件处理展示和局部交互，复用流程放composable；只在确有跨组件共享需要时提升状态。
- 组件不直接散落HTTP调用；通过功能api适配调用生成客户端。生成文件不手改，HTTP/WS合同变更在生成及合同检查中验证。
- shared不导入admin/student业务；两端不互相复用私有实现。颜色、间距和状态样式沿共用变量与组件，不在每页另定义一套。
- 明确加载、空、错误、成功状态；可交互元素支持键盘、焦点和可识别标签。页面隐藏或禁用不能代替服务端权限。
- 释放watch、定时器和订阅；旧请求、旧账号的晚到响应不得覆盖当前状态。不得用浏览器本地推断代替服务端活动或掌握状态。

常规TS模块按导入、类型／常量、实现、导出组织；类型导入显式`import type`，可不变值用`const`，禁止`var`、通配符业务导入和无说明的非空断言。公开能力写简短JSDoc说明异步、失败或清理约定；不为每个props重复写注释。SFC按script、template、style保持一致，样式作用域明确，列表使用稳定key，不直接修改props。

ESLint检查代码问题、Prettier负责排版、vue-tsc负责TS及模板类型。Vite构建成功不能代替类型检查。第三方声明的`skipLibCheck`不跳过本项目源码和Vue模板。

## 5. 脚本和配置

### 5.1 脚本

Bash负责薄编排，复杂结构处理用Python。Bash使用`set -euo pipefail`，同时显式处理预期失败；该设置不能替代错误处理。参数用数组传递，变量正确引用，避免`eval`和拼接可执行命令。

脚本按文件说明、shell选项、函数、`main "$@"`组织；函数局部变量用`local`，一行声明一个变量。带命令替换的赋值与`local`分开，避免掩盖命令失败。复杂函数注释说明参数、输出／退出码、环境依赖及副作用；简单错误输出函数无需重复说明显然语义。

解析、校验和执行分段；未完成输入校验前不得修改外部状态。数组保存命令参数，不使用字符串拼接执行；路径必须引用。循环和case展开写，长命令按参数组换行，不用连写`&&`／`||`模拟多分支。明确判断命令返回值，不能仅凭输出文本声称成功。

集群、namespace和配置文件显式指定；不修改默认context、不自动覆盖凭据。重复运行不删库重建，失败非零退出。测试和维护只清理本次创建的临时资源，清理不扩大到未知路径或PVC。耗时外部命令有上限。

### 5.2 配置与依赖

YAML/JSON采用2空格。参数说明写清用途、单位、默认值/必填性；环境配置覆盖部署差异，业务常量不能偷偷变成运维参数。配置加载验证类型与范围，缺关键项立即失败。

密码只通过Secret或环境安全注入，不写入Git、示例、测试输出。版本采用固定值；镜像按digest、官方Chart按校验值锁定。npm工具用`npm ci`，Python工具使用固定依赖文件；检查过程不得自动安装或升级工具。

普通YAML检查重复键、缩进和类型歧义；Helm模板先渲染后检查，不能直接交给普通YAML格式化器。自有Chart用values Schema约束必要字段和类型；上游Chart不复制修改。渲染/静态校验不代替真实集群API和运行测试。

### 6.1 测试写法与自动检查

测试按准备、执行、断言、清理分段；每个用例说明验证的行为。失败输出能指出是哪一场景，参数化场景用`subTest`或等价方式。探测真正的失败原因，不能把网络故障误当权限拒绝；不通过扩大时限、弱化断言或跳过测试来获得通过。

本地替身与真实测试分开；真实环境必须显式指定目标。外部命令有上限，临时资源有运行身份并登记清理，不打印敏感输入。重复执行应可区分本次资源，不清理其他人的数据。测试超时、清理失败和重跑均留下记录。

每次增量先运行静态检查，再执行本项必要测试及受影响回归。数值、权限、事务、幂等和恢复边界须有断言；不靠覆盖率数字或镜像实现的测试证明业务正确。真实模型验证独立启用并限制用量；固定替身不能替代真实接线和教学质量验收。

检查失败应修正原因。确需例外时只限具体行/规则，并写原因；影响合同、安全或公共规范的例外先由用户确认。禁止跳过检查后仍报告通过。缺工具直接失败；没有正式源码的检查明确报待接入。

每次交付保留运行编号、代码基线、工具版本、命令、结果和未覆盖范围。格式化单独显式执行；评审关注业务行为、可读性和异常处理。工具通过后仍须自检及用户评审。

### 6.2 人工评审门槛

工具检查通过后仍逐文件检查，交付记录须给出结论或未解决项：

| 检查面 | 人工确认内容 |
| :--- | :--- |
| 职责与结构 | 文件／函数职责明确，主流程可顺着读；没有无关重构或新增抽象 |
| 排版与命名 | 分段对应逻辑，长表达式可读，无多个动作挤一行或含糊缩写 |
| 注释与合同 | 入口、关键约束、副作用和失败处理说清楚；注释与代码一致，不逐行复述 |
| 正确性与边界 | 正常／失败／重复路径可解释，资源释放、目标隔离、权限、幂等和事务没有被削弱 |
| 安全与观测 | 不泄露凭据；错误保留原因，日志遵循唯一合同，失败不能报告成功 |
| 测试与交付 | 断言保留，实际运行结果及未覆盖项明确；文档／配置／代码一致，用户评审后才标完成 |

评审记录跟随本次小增量，引用具体文件和关键例子，不用“工具全绿”替代人工结论。提交范围须聚焦；说明做了什么、为何调整、如何验证及剩余限制，不把未实现部分写成已完成。
