> **版本**：v0.2<br>
> **状态**：规范草案；试点文件评审通过后按批次落地<br>
> **维护与评审**：Codex 编写及自检，用户审阅<br>
> **更新日期**：2026-11-25<br>
> **修订说明**：v0.2 强化函数内注释：判断分支、循环与逻辑块原则上必须加注；明确注释标准为帮助理解、不写废话；补块级注释模板与验收指标。注释语言、结构与上位规则沿用[编程规范](Coding_Standard.md)，本册不另设业务规则<br>

## 1. 范围与定位

本册只覆盖 `src/m1/server/src/deermind` 后端 Python 代码的存量注释补齐；前端 `clients/`、测试夹具、脚本与生成物不在本轮范围。

注释的上位规则（中文注释、不逐行复述、docstring 结构、类型由标注维护）已在[编程规范 §1.2、§2、§3.1](Coding_Standard.md)确定，本册只补四件上位规则未展开的内容：

1. 文件头、类、函数、行内注释的具体模板；
2. 哪些代码必须注、哪些应当注、哪些不注；
3. 存量补注的批次与优先级；
4. 每批的验收与留痕要求。

注释解释**为什么这样做、边界在哪、谁负责**，不解释语法是什么；不以增加注释掩盖结构问题（[编程规范 §2.1](Coding_Standard.md)）。

## 2. 语言与格式约定

- 解释性文字统一**中文**；标识符、协议名、事件类型、错误码、Ref 类型、数据库字段保留英文，不翻译。
- docstring 采用 Google 风格简短段落；复杂接口可用「入参／返回／副作用／边界」小节，简单函数一段即可。不用 reST `:param:` 装饰。
- 类型已由函数标注维护，注释不重复抄写参数类型和返回类型。
- 模块、类、函数说明用三引号 docstring；文件头不使用 `#` 注释块，与现有源码风格一致。
- 行内说明用 `#`，缩进与被说明代码块对齐；不保留大段注释掉的代码。

## 3. 注释分级

### 3.1 A 级：必须注释

跨层契约、业务规则和非显然决策，缺了后来者无法判断边界：

- 模块对外暴露的主要类型、函数、事件类型，及其被谁消费；
- 事件追加、投影写入、收据保存、等待登记等副作用；
- 顺序与并发约束：空间事件序号、active 占用阻塞、锁与租约、幂等键与去重口径；
- 取材与授权边界：固定采用版本/快照、获准 Task 范围、不读草稿/私有记忆/AI 完整请求；
- 派生事件不再触发同一增权、技术失败不构成反证等关键业务决策；
- 非显然的换算、阈值来源、与设计文档条款对应的规则。

### 3.2 B 级：应当注释

公开接口和有一定复杂度的实现，补清调用约定；**函数体内的判断分支、循环和逻辑块是注释重点，不因属于内部实现而省略**：

- 函数用途、非自解释参数语义、返回值状态含义、主要异常与冲突处理；
- 类的职责边界、协作方、状态进入与退出方式；
- 一个函数内多个逻辑块（准备输入、执行动作、校验收尾）各自的目的；
- 每个 `if/elif/else`、`try/except` 分支在核验什么条件、命中后走哪条路、挡的是哪一类非法/重复/过期/越权状态；
- 每个循环遍历什么对象、逐条处理什么、累积什么、何时退出；
- 与既有代码不同的处理方式及其原因。

### 3.3 C 级：不注释（豁免）

仅当代码与动作都完全自解释时不补注释，避免制造维护债务：

- 一行 `return`、简单 getter/赋值、Pydantic 字段声明；
- 条件与动作都一目了然的单行 guard（如 `if not x: return`）；
- 名称已说明对象或目的的局部操作；
- 纯转发、纯类型别名、常量定义。

**判断与循环原则上不进入豁免**：哪怕只做一件事，只要条件含业务规则、阈值、归属/状态/期限核验，或循环有累积、过滤、去重、校验目的，都按 B 级加注。是否处于豁免边界拿不准时，按 B 级写一句简短说明，不强行凑模板段落。

## 4. 注释模板

### 4.1 文件头（模块 docstring）

紧贴文件首行，先一句话说明职责，再补分层定位、对外契约和边界约束；后两段无内容时省略。

```python
"""<模块一句话职责：本模块负责什么业务或底座能力>

分层定位：<abstractions / foundation / infrastructure / product / spaces / bootstrap / entrypoints 之一>
对外契约：<主要公开类型、函数、事件类型及消费方；仅本层内部使用时写明>
边界约束：<本模块不做什么、不可绕过的约束；无则省略本段>
"""
```

### 4.2 类注释

```python
class XxxService:
    """<类一句话职责>

    职责边界：<只做什么，不做什么>
    协作方：<依赖的端口或服务，或被谁调用>
    不变量：<并发、幂等、状态生命周期约束；无则省略本段>
    """
```

### 4.3 函数注释

```python
async def receive(self, db: AsyncConnection, notice: EventNotice) -> Acceptance:
    """<函数用途一句话：做什么业务动作>

    入参：<非自解释参数的业务语义；类型已标注的不复述>
    返回：<返回结构与各状态含义>
    副作用：<追加事件 / 写投影 / 存收据 / 登记等待；纯读取时写明>
    边界：<幂等键、授权范围、失败与冲突处理；无则省略本段>
    """
```

- 公开入口、有副作用或重要异常的函数必须写；简单私有函数按 C 级豁免。
- 测试方法说明其保证的行为，不复述函数名。

### 4.4 行内注释

**注释标准**：读完注释能判断这段为什么存在、边界在哪、失败/重复/过期时怎么走；注释意图、规则和约束，不复述语法、不翻译表达式、不写"遍历列表""赋值给 x"这类废话。拿不准是否有独立价值时，倾向于不写。

**注释对象**：

- 逻辑块：函数内按准备输入、执行动作、校验结果/收尾分段，段首一句说明本段目的；
- 判断分支：说明该判断核验什么、命中/不命中分别走哪条路、挡的是哪一类状态（旧尝试、输入漂移、重复提交、越权、过期、缺失事实等）；多条件分组时逐组说明含义，不把一串 OR 压成一句；
- 循环：说明遍历对象、每条记录处理什么、累积/过滤/去重什么、退出条件；
- 非显然换算、阈值来源、顺序/锁/租约/去重点；
- 存疑点写 `# 待核对：<疑问点>`，不补造规则或业务结论。

**写法示例**（注释仅示意，实际以源码与设计合同为准）：

```python
# 已受理过同一请求：沿原工作返回，异输入/异范围判身份冲突，不重复建工作。
if existing is not None:
    ...

# 逐条核对登记类型、生产者与读取范围；任一项不符即拒绝，不进入正文解码。
for draft, registration in zip(drafts, validated):
    ...

# 先锁业务范围再取执行锁；顺序固定，收尾不能反向获取业务锁，避免死锁。
```

- 行内说明用 `#`，缩进与被说明代码块对齐；单行注释长度不超过被说明代码块的三成；
- 同一逻辑块内不重复贴相同结论；注释与代码改动同步更新，发现过时先修正。

## 5. 编写纪律

1. **先理解再落笔，注释必须有依据。** 先把函数拆成逻辑块、弄清每个判断与循环的意图，再写注释；注释内容必须能在当前代码或 `doc/mvp` 设计/合同条款中找到依据；禁止由模型反推业务规则。设计条款与代码不一致时，先记录疑点，不改写注释去迁就任一方。注释不为凑模板复述代码，理解不到位的块标 `待核对`，不硬写结论。
2. **不改变代码行为。** 本轮只插入注释和必要空行；不重构、不改名、不调整逻辑、不动导入顺序（格式化交给既有工具）。
3. **注释与代码一致。** 后续修改逻辑时同步更新对应注释；发现过时注释先修正，不能带着失真注释继续叠加。
4. **存疑留痕。** 取不到依据的业务判断标 `待核对`，不写成确定结论；待核对项在批次交付记录中列出。
5. **不泄露敏感信息。** 注释不写密钥、凭据、内网地址、完整模型请求；引用配置只写配置项名称。

## 6. 批次与优先级

按分层复杂度和契约价值排序，每批独立提交，便于回滚和复核。

| 批次 | 范围 | 选取理由 |
| --- | --- | --- |
| 1 | `abstractions/` | 跨层合同，注释最该准确；文件量最小，先立样板 |
| 2 | `foundation/` | 底座规则集中：事件、执行、等待、AI 调用与预算 |
| 3 | `spaces/evaluation/`、`spaces/interaction/` 核心服务 | 业务复杂度最高、规则与边界最多 |
| 4 | `product/` 业务服务 | 次核心业务，事务与授权规则为主 |
| 5 | `bootstrap/`、`entrypoints/`、`infrastructure/` | 装配、接口与适配层，多数自解释，注释从简 |

### 6.1 单批流程

1. 按模板生成注释草案；
2. 对照源码与所属设计分册核对语义，标出存疑项；
3. 编译与导入检查通过；
4. 跑通该范围已有单元/迁移测试；
5. 人工抽查契约类文件注释准确性；
6. 单独成 commit，提交说明写明范围、核对依据和剩余待核对项。

## 7. 验收要求

- **语法**：全量 `python -m compileall` 通过；注释不引入语法或导入错误。
- **测试**：该批次相关已有测试通过；注释不进入测试断言，测试结果不替代注释准确性人工抽查。
- **覆盖率口径**：A 级契约与规则注释全覆盖；B 级公开接口与复杂函数补全；**复杂函数内的判断分支、循环与逻辑块须有块级注释**；C 级豁免不设指标。
- **一致性抽查**：每批至少抽查跨层合同文件，核对注释中的事件类型、授权范围、幂等键与源码/合同一致；并抽查 2–3 个复杂函数，顺着主流程能读懂每个分支与循环的意图，注释不复述代码。
- **环境限制**：本地依赖不完整时，编译与测试以 WSL/Linux 环境 `scripts/test.sh` 为准；不能据源码阅读推断回归通过。
