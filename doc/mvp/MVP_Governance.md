每类内容有明确的维护位置。其他文档通过编号与链接引用，仅补充本层责任，不复制一套并行的决定、指标或追溯表。

异常处理分层：需求规格说明必须发生的行为；交互设计说明呈现与操作；数据设计处理数据和授权相关异常；工程设计落实机制。发现冲突时定位错误或新的约束来源，按 §5 修正或重开相应决定，不能简单宣布某份下游文档优先。

用户故事用于说明角色、情境和期望价值；关键功能还须有前提、输入、主要业务过程、结果与状态变化、规则、例外和 AC。产品对象及其业务关系由 Requirements 定义，领域含义引用正式 Space 设计，界面组织由 Product 设计，授权矩阵由 Data 细化，物理存储与接口由 Engineering 落实。同一条规则不因换成“活动合同”或“维护状态”而获得第二个决定位置。

每份主体文档明确输入、输出、直接接收者和接收条件。G3 交付产品承诺，G4 交付操作方案与实际基础资产，G5 交付真实实现和证据。Phase 4 资产需有标识、版本、引用、来源、适用条件、参考与审查记录，可在正式运行时完成前检查；Phase 5 实现导入、执行和结果记录，并核对语义与版本未在接入中丢失。阶段可以有受控反馈，不以尚未完成的下游软件作为上游内容定义的必需前提。

完成证据分别说明文档是否具体、资产是否存在且合格、工具是否能够执行、是否实际运行及结果如何。没有真实模型成功路径、只有固定响应或全部未决，不能证明核心功能已经实现；有限语义测量也不能代替后续正式质量和价值判断。各指标适用节点只由 Validation 维护，各 Gate 引用。

## 2. 元信息、基线与引用

文档头、分类写作及检查方法遵守[设计文档规范](../top/DeerMind_Design_Document_Standard_v1.0.md#2-文档头与状态表达)，使用标题后的统一引用块；README 采用精简文档头。本文只补充 MVP 的责任与基线管理，不维护第二套通用写作规范。未确定人员或版本时明确标为待指定，不填入虚构名称、提交或评审结果。责任可以由同一人承担，不新增必须两人审核的要求；实际提出者、判断者及依据须可查。

工作草案由 Git 保存修订，不要求每次改字都手动升级文档版本号。正式评审引用的内容须可准确恢复：登记基线标识、文档与源码的准确提交，以及未纳入 Git 的资产版本、位置和校验信息。尚未提交的内容不得只用 HEAD 代表；应先形成可恢复的评审快照。正文链接方便导航，不能代替版本依据。

G3/G4/G5 的评审记录分别列出实际审查的基线。通过后可以用唯一的 Git tag 标记对应提交，仍需保留准确提交号及外部资产清单；不移动旧标签来改写已评审内容。新修订形成新记录，并说明旧基线与结论是否仍适用。本轮 G3 使用可恢复的内容快照和清单固定批准输入，尚未创建 Git tag；后续不能以 HEAD 或当前文件代替该准确基线。

| RISK-008 | 面对变化题目与课程时，模板过度拆分或合并、组合及方法差异表达不清；个人判断与选题因此失真，或内容维护难以持续 | SRC-022 保留用户疑问；纸面案例和旧机制验证尚不能证明现行领域模型的实际适用性 | OPEN-006；HYP-001–004；学习情况、评价、选题与领域管理 | 按 DEC-017 在现有交付中检查真实材料的映射、多解、组合和责任差异；区分内容缺口、实现错误和表达能力缺口，保留反例与版本，按 Validation §3.1、§6 处理 | Phase 4 实际内容与参考审查、Phase 5 运行及维护、Phase 6/7 质量与使用；明确影响当前交付的冲突及时提出 | 开放；概念归属已明确不等于适用性已验证。不要求先证明覆盖所有未来课程；实际缺陷按所属层处理，不预先承诺都能靠工程优化解决 |

不确定、不清晰的事项必须显式提出；涉及方向、范围、用户承诺或上位合同的选择须讨论，不得用实现默认值自行决定。属于后续阶段的细节登记其边界和决策节点，不必提前完成。允许后置的事项应说明为何不损害当前阶段成立的条件；关键前提未知不能只挂一个责任人就视为可交接。

## 5. 变更与影响分析

文字纠正和链接修复可直接处理并检查，不为此增加批准流程。已经确认的范围、责任、行为承诺、成功标准或上位合同改变时，按以下顺序处理；已有有效授权可直接引用，不重复索要确认。

1. 记录变更原因、原决定或基线、拟改变的内容及依据。
2. 经追溯主索引检查受影响的需求、活动、数据权限、领域与评测资产、实现和验证结果；列出不受影响部分及理由。
3. 由相应责任层作出决定，登记实际确认来源、承担者和日期；涉及新的产品取舍时提出讨论。
4. 更新权威正文与关联引用，标记受影响而尚未完成更新或重测的交付；不能让它们继续以无条件有效状态进入下一 Gate。
5. 按影响补充有限的检查与评审，形成新基线或修订记录。既有结果按原版本保留，不把旧失败改写为通过，也不因任何小修改就自动重开全部阶段。

## 6. 统一追溯与证据索引

需求关系只在[需求规格 §7](phase-3-definition/MVP_Requirements_and_Acceptance.md#7-统一追溯主索引与交接)维护主索引，以需求编号连接问题来源、决定、验收场景、设计对象、资产、实现和结果。阶段完成后追加实际引用，不提前编造下游条目。各文档保留自身对象编号、版本及详情，通过主索引查看跨文档覆盖，不另建可独立编辑的完整覆盖表。

主索引可以按多对多关系分行或形成视图，不要求一张无限加列的表。材料清单、权限矩阵和阶段证据清单仍各司其职；它们描述材料、授权或本次评审，不成为第二套需求追溯关系。

Phase 3 的原始依据索引由[产品定义 §1](phase-3-definition/MVP_Definition.md#1-问题背景与依据)维护，至少记录来源编号、类别、出处或文件、日期与版本、支持的判断及限制。区分用户陈述、直接观察、理论或研究、经验推断和未验证假设；没有原始证据时如实写明。不强制新做访谈、竞品分析或重新询问个人困难。外部原始材料可存于合适位置，索引须可定位并说明访问条件；未取得的材料不得作为已核实依据。

## 7. 术语与编号规范

公共产品术语在下表统一登记，上位系统术语引用其权威定义，不另行改写。局部术语由对应领域或设计文档解释并链接回来。本轮先登记易混淆的产品概念，不重定义系统内部对象。

| 术语 | 简明含义与使用边界 | 权威定义位置 | 相关或易混淆术语 |
| --- | --- | --- | --- |
| 问题求助 | 对不会、卡住、存疑或错误的具体题目请求帮助，不预设已经产生错误作答 | 产品定义 NEED-001 | 与错题记录区分 |
| 主动介入 | 系统依据有效判断和目标提出适当后续行动，可服务保持、迁移或补充证据；保留学生控制 | 产品定义 NEED-006；既有 Interaction 责任 | 不等于固定提醒或强制测验 |
| Learning Space / 课程空间 | 管理 LearningMaterial、范围与 LearningTarget，引用个人历史的授权视图 | [学习空间设计](../concept-design/DeerMind_Learning_Space_Design_v1.0.md)；CON-002 | 不等同 Domain Space，不是第五个核心 Space |
| Domain Space / 领域空间 | 共享的 ProblemTemplate、SolutionTemplate、KnowledgeComponent 及其关系 | [Domain 设计](../concept-design/DeerMind_Domain_Space_Design_v1.0.md) | 不拥有个人目标或 LearnerBelief |
| 错题记录 | 带来源、实际作答及确认状态的学习记录；没有作答或有争议时保留相应状态 | 产品定义 NEED-005 | 不等于已证实知识薄弱，也不是唯一 Evidence 来源 |

对象编号以类型区分，在同一类型内唯一、稳定且不重复使用。需求候选与正式行为需求分别使用 NEED、REQ；来源使用 SRC，价值假设使用 HYP，验收场景使用 AC，指标使用 MET，实际案例使用 CASE，结果使用 RES；决定、约束、待决事项和风险分别使用 DEC、CON、OPEN、RISK。活动、流程和界面可使用 ACT、FLOW、UI。采用“类型-序号”，填充时才分配实际编号；编号本身不表示已批准。

旧文档的编号保留其原义，通过“归档文件 + 旧编号”引用并登记与新编号的对应，不直接复用导致历史语义改变。对象删除或合并保留停用与替代关系。

## 8. 填充、检查与交付规则

大纲阶段各章文字是撰写要求，不是项目事实。正式填充时逐章替换为依据、决定或设计，移除已完成章节的写作提示；仍未完成的部分保持明确状态。必备产出只在适用的关键章节指定，其他章节可用清楚的连续说明，不为形式强制每章配图表。

各主体文档最后一章使用完成检查项。每项评审补充“已满足／未满足／不适用”、依据位置、实际判断人及日期；不适用须解释，勾选本身不构成证据。文档完成与资产完成、阶段通过分别判断，正式阶段结论只登记在 [Gate 记录](MVP_Gate_Reviews.md)。

日常修订保持稳定文件名，不按轮次复制过程文档。README 保留阶段、导航和当前状态；向外提供评审包时附准确版本和依赖清单，包含核对所需的上位依据或可访问引用。若未提供 Roadmap、所引用历史决定或资产，应明确此次评审不能核对的部分，不能据局部打包材料宣称全量承接完成。
