## 1. 目的与架构位置

Learning Space 是组织一次课程或学习范围的容器，例如同一学习者的校内数学与校外辅导。它让用户知道自己使用哪些材料、学习什么、以什么要求判断目标达成。Domain Space 则提供可被不同课程与目标复用的问题、方法与知识定义。两者有引用关系，但不是同一个对象的两个别名。

本设计承接原架构 Learning Space 中 LearningTarget 的规范定义责任，并明确 LearningMaterial 的位置。Learning Space 是正式名称；其架构位置属于产品层（Product Context），不是 Domain、Evaluation、Interaction、Evolution 之外的第五类核心认识空间，也不增加一个独立推理引擎或部署服务。

本文只定义课程容器、材料、目标及跨空间责任，不决定 MVP 界面、自动排课、教材选择、完整权限矩阵或工程数据结构。既有用户约束由 MVP 治理登记承接，不能从通用架构能力反推首版必须开放全部功能。

## 2. 核心对象与信息归属

Learning Space 持有自己的身份、适用用户与权限范围、LearningMaterial 及其组织结构、LearningTarget 及当前采用的版本和范围。它可以引用相关运行历史与学习者状态的视图，但不成为 Event、Evidence 或 Belief 的第二写入者。

| 对象或关系 | 规范责任 | 关联而不拥有的内容 |
| --- | --- | --- |
| LearningMaterial | 保存材料来源、版本、内部章节与内容引用，说明可用范围 | Domain 的问题、方法和 KC 定义 |
| LearningTarget | 定义学习范围、期望质量、条件、责任与成功语义 | 对某人的目标达成判断、教学计划 |
| 材料到领域的映射 | 指明哪段内容关联哪个版本的模板、方法或 KC，并保存依据与未决状态 | 对个人掌握的推断、对规范 Domain 的私自修改 |
| TargetBinding | 连接学习者、学习空间与正式目标的运行关系 | 发生事实由 Event 记录，当前有效投影由 Interaction 维护 |

Domain 定义可被共享，不意味着个人 Evidence 可以跨课程自动混用。数据用途、用户授权和评价适用范围仍需检查。当前 MVP 已确认校内与校外两个空间的个人学习历史、Evidence、Belief 和推荐上下文隔离；引用同一规范 KC 不能绕过这一约束。

## 3. LearningMaterial 与领域映射

LearningMaterial 可表示教材、讲义、课程资料或其他学习材料。章节、小节、页面和内容片段是材料内部的结构与定位方式，不为它们新增一级 MaterialSection 模型。这里选用 Material 而非 Textbook，是为了避免把所有学习来源限定为纸质教材。

原始材料、识别结果、内容解释、领域映射和正式领域定义具有不同地位。扫描与识别先保留来源；章节结构、题目和解法提取可能有错误；将内容映射到模板或 KC 是需有依据的解释；只有受控发布的定义才取得 Domain 的规范地位。教材中的答案与分类是参考来源，不能自动成为无条件正确的规范事实。

映射应记录材料及内部位置、被引用的领域对象与版本、关系含义、依据和当前状态。一节可关联多个模板或 KC，同一领域对象也可被多个章节引用。映射覆盖不完整时，范围检测和章节统计应说明尚未覆盖的部分，不把“没有映射”当作孩子不会，也不把章节标题直接变成能力标签。

管理员维护材料与映射时，可以提交新增或修订领域对象的候选，但两类正式修改分别经过对应 owner 的受控路径。产品可以提供统一操作流程，却不能因此让一个材料标签编辑静默改变所有课程共用的 Domain 语义。扫描导入与人工核实的具体界面、批量处理和审核粒度在 Phase 4/5 细化。

## 4. LearningTarget：定义学习范围与要求

### 4.1 目标来自现实目的，但不等于原始请求

GoalIntent、ExternalStandard／Obligation 与正式 LearningTarget 必须保持区分。学习者想“学会分数除法”、学校要求完成一章、认证规定通过某项考核，都可以作为目标来源，但需要解释为有范围、有条件、可评价的学习要求。制度要求在其适用范围内有约束力，不自动成为整个领域能力的唯一真理。

正式 LearningTarget 由 Learning Space 的目标定义责任拥有。Domain 提供引用坐标和适用限制，不预设所有产品都应采用同一个目标。目标可以直接来自明确学习目的，不强制必须有一份教材才能建立；具体产品是否只允许按教材选范围，仍由其需求决定。

### 4.2 最小充分语义

| 目标组成 | 必须说明的问题 |
| --- | --- |
| 范围与引用 | 引用哪些 TaskTemplate、参数与情境变化；关联哪些教学与解释 KC；依据哪个材料与 Domain 版本 |
| 方法要求 | 哪些 SolutionTemplate 可用；允许任选一种、指定方法，还是多个方法分别覆盖；适用性与子任务约束如何继承 |
| 期望责任 | 要求计算、理解、选法、组织、解释、验证等哪些实际表现；哪些尚未要求 |
| 质量与成功语义 | 达到怎样的正确性、解释质量、稳定性或迁移范围才有理由说目标成立 |
| 默认评价覆盖 | 每个选定任务引用单模板 Claim 版本及其内部方面；默认独立、理解、迁移、保持。目标记录采用方面、标准及有依据裁剪／扩展，跨任务要求通过目标组织 |
| 条件 | 判断成立的环境、工具、变化范围、时间或风险限制 |
| 支持与责任边界 | 哪些工作由学习者自己承担，哪些可以交给工具、AI 或他人 |
| 来源与可评估性 | 要求的来源与权限、版本、适用范围，以及原则上可支持或反驳它的证据 |

Learning Space 对共享 Domain 作有范围的引用，不复制或裁剪全局 TaskTemplate。方法选择须沿实际递归分解检查适用范围；被排除的方法若仍数学上正确，不能被判成数学错误，但不能冒充已满足指定方法的目标。新增未审核方法先保留映射未决，不能靠选择规则把它当成正式已覆盖方法。

同一目标纳入方法 A、B 时，知识覆盖可包含两者 KC 的并集；“纳入”不自动意味着两法均须掌握。同一模板、同一评价条件以一个多维 Claim 组织责任，不按四个维度分建声明。方法 ANY、指定或 ALL 等含义不同的评价条件须绑定明确的适用定义／版本；仅提高目标门槛或改变所需方面不必复制 Claim，也不直接改变 Belief。

这些组成是语义要求，不强制最终成为同名字段。目标不退化成 KC 清单或单一分数；尚不能明确的部分应保留未决和使用限制。测得了什么只能支持相应范围的判断，不能为了便于测量把真实学习目的悄悄改成“完成几道题”。

例如，目标 A 要求在分数分组问题中独立建立数量关系并求解；目标 B 允许给出关系式，只要求正确计算。两者可引用同一 TaskTemplate，却具有不同支持与责任条件。Domain 中的方法保持相同，Evaluation 对两种条件下的表现分别解释，Interaction 据此选择合适帮助。

四维在单模板 Claim 内定义，目标可以选择多个任务及各自方面，不把整个课程绑定为一个跨模板 Claim。一个目标要求可以综合多个方面，但每项判断须能追溯具体依据；章节统计仍按已发布学习要求计数，不按模板数乘四。目标采用的方面尚未定义完整是准备缺口，已定义但无证据是认识不足，不能改成不适用。

四维通用定义及 Task Claim 语义以 [Evaluation §3.1](DeerMind_Evaluation_Space_Design_v1.5.md#31-learner-state-model定义-deermind-可以相信什么) 为准；目标发布记录采用、裁剪与扩展的理由及影响。首版由管理员维护并审核规范内容，学生选择已发布目标及范围；不能通过聊天删掉表现较弱的维度。

### 4.3 目标、问题与工具边界

TaskTemplate 的完成要求规定一道问题需要解决什么，LearningTarget 则规定在一组问题上期望形成什么水平的能力。目标的分解可以辅助检查覆盖，不等同教学顺序，也不自动证明先修关系。

工具语义保持三个来源：Domain 定义某类问题在什么工具条件下仍是同一类责任；LearningTarget 定义目标允许外部化哪些责任；Interaction 与 Event 表达当时工具是否可用、实际上用了什么。允许使用某工具不等于已经使用，实际使用也不必然越界，必须按目标及 Claim 条件判断。

## 5. 从目标定义到实际运行

目标定义与目标选择分开。AI 可以解释意图、提出 TargetCandidate 或 TargetBindingCandidate，但自然语言输出没有自动修改正式目标的权限。产品侧经授权的目标定义路径负责创建、修订和发布；选择、接受或切换一个已有目标按已有产品权限执行，不必因此进入一次系统结构演化。

TargetBinding 的发生事实进入全局 Event；关系是否具有合法来源和作用范围由 Product Context／Context Constitution 约束；Interaction 负责当前有效的 binding projection。Binding 应明确学习空间及目标版本，不能只保存一个无版本目标名称。

运行时先解析当前材料范围、目标、Domain 版本和授权，再选择或形成具体问题与讲解活动。实际提交与帮助形成 Event，Interaction 生成 Observation，Evaluation 解释 Evidence 并维护 Belief。TargetAssessment 比较正式目标与有效 Belief，说明已支持、未达要求或证据不足的部分；它是可缓存的派生结果，不另建 TargetBelief。

学习者能力不足与系统不知道能力是否足够是不同结论。TargetGap、EpistemicGap、Readiness 都不直接发出教学命令；是否讲解、测验、等待或不干预由 Interaction 决定。目标已经达到时可以减少支架，不能为了完成系统计划而不断增加任务。

## 6. 权限、版本与失效传播

材料、映射、目标、Domain、Claim 和 Policy 应有可分辨的身份及版本依赖。可以统一打包发布相容的组合，但不能用一个含混的“最新课程版本”覆盖各自来源。Task Claim 的任务范围、方法覆盖或完成责任发生变化时，应建立明确的新语义版本或新命题，并按依据重新解释；旧命题不能仅因目标更新被判为能力下降。跨空间关系需能追溯到所用具体版本；定义记录、发布状态与当前绑定也不能互相替代。

仅改变目标选择的方面或门槛时，重算 TargetAssessment 及受影响的决策输入，不直接改变多维 Belief。若改变 Claim 内部方面定义、方法责任、迁移变化或保持条件，则发布明确新版本，逐方面核对兼容和实际依赖；新方面不复制其他方面判断，不因一方面重算刷新全部证据时间。裁剪目标要求不能显示成能力提升；教材排版或章节位置改变也不自动重算全部能力。

材料或映射错误可影响题目解读、范围覆盖与统计，需要定位实际依赖并重新解释相关结论。纠正历史解释不改变当时原始上传、实际展示与作答。用户可见删除、内部保存用途和彻底删除的产品规则按已确认需求和数据权限合同执行，本文不另开一套删除政策。

正式结构或责任语义的变更遵守 Governance；Evolution 可以分析目标或映射失配，不能因为目标未达就自动降低目标，也不能借修改材料扩大数据使用范围。各责任层可共用技术设施，语义写入权仍须分别检查。

## 7. 决策依据与适用限制

本设计把目标置于学习空间，是因为不同课程和学习目的应能复用同一领域定义。若把目标永久固化在 Domain 中，领域覆盖容易随单个课程收缩；若只保存自由文本意愿，评价又缺少稳定标准。当前方案保留正式目标的规范性与版本治理，同时避免其拥有个人认识或行动策略。

代价是多了一组明确的跨层引用，需要维护目标、材料映射与 Domain 版本的相容性。若后续出现跨产品共享目标包，它仍是可复用的产品目标定义，而不是据此把目标重新放回 Domain。是否需要这种共享产品能力，不在本轮扩展范围内。

目标有效性、章节映射质量及能力统计口径仍需实际领域资产和评测。数学与 Kubernetes 的概念例子只检验表达边界，不能证明系统已经适用于所有领域或形成持久学习收益。重要反例应进入模型或产品边界复核，普通实现缺陷则在实现阶段直接修复。

## 8. 交接与完成边界

本轮交付目标与材料的正式 owner 合同，并由概念总览、三个其他 Space 和 System Design 同步引用。材料维护、目标解析、引用解析、版本发布及 typed invalidation 的具体实现继续进入 MVP 后续阶段；旧 Spike/Build 的输入、失败与通过结论保持其原有版本范围。

原 Learning Space Design 的 Target source、success semantics、support boundary、Definition／Binding 分层、TargetAssessment 派生性及版本历史约束在本文 §4–6 承接；Domain 中不再保留另一份可修改的目标定义。MVP Gate 是否满足仍以对应交付与真实证据判断，本文件完成不替代 G3、G4 或 G5 的批准。
